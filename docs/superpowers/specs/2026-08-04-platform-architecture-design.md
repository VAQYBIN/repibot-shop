# Re:Pibot Shop — архитектура платформы

Дата: 2026-08-04
Статус: утверждён
Область: вся платформа. Отдельные подпроекты имеют собственные спецификации.

---

## 1. Что строим

Магазин VPN-подписок поверх панели Remnawave 3.2.1. Продажа и обслуживание идут через Telegram-бота, Telegram MiniApp и веб-сайт. Проект открытый: любой может развернуть его у себя рядом со своей панелью.

Три группы пользователей:

- **Клиент** — покупает и продлевает подписку, управляет устройствами, обращается в поддержку, приглашает рефералов.
- **Персонал** — админ и сотрудник поддержки, работают через веб-админку и Telegram-супергруппу.
- **Оператор развёртывания** — поднимает проект у себя из `compose.yml` и переменных окружения.

## 2. Принятые решения

| Решение | Выбор | Причина |
|---|---|---|
| Роль бота | Тонкий: вход, уведомления, оплата Stars, тикеты | Один клиентский UI вместо двух реализаций каждого сценария |
| Аутентификация | Целиком на Python, Better Auth не используется | Бэкенд на FastAPI; отдельный Node-рантайм ради auth не окупается |
| Модель тарифа | Тариф = Internal Squad + лимиты | Штатный механизм панели, позволяет продавать разные наборы локаций |
| Подписки на пользователя | Одна активная + подарочные ваучеры | Простая модель, одна ссылка-подписка навсегда |
| Фискализация | Без чеков; поля `receipt` заложены и выключены флагом | Решение владельца проекта. Включение потом — конфиг, а не переделка |
| Автоплатежи | Есть, через сохранённый метод YooKassa | Основной рычаг удержания |
| Подарки | Одноразовый код-ваучер | Не требует знать получателя заранее, переиспользует механику промокодов |
| Языки | Русский и английский | Открытый проект без английского не устанавливают |
| Размещение панели | Оба варианта: рядом и удалённо | Адрес и токен — переменные окружения |
| Масштаб | До ~5000 пользователей | Один экземпляр каждого сервиса, очередь на Valkey |
| Триал | Один на Telegram-аккаунт | Почту накрутить тривиально |
| Реферальная награда | Фиксированная за первую оплату реферала | Проще считать и объяснять, не уходит в минус |
| Email | Интерфейс `EmailSender` + SMTP по умолчанию | Каждый разворачивающий подключит своё |
| Цена в Stars | Отдельное поле у тарифа | Полный контроль над маржой, нет зависимости от курса |
| Роли | `admin` и `support` | Добавлять роли в работающую систему дороже, чем заложить сразу |
| Фронтенды | Два приложения над общим `packages/core` | SPA в Telegram и SSR в вебе — разные среды, общая логика |
| Клиент Remnawave | Генерация моделей из OpenAPI + ручная обёртка | Типы сходятся с панелью, есть куда положить ретраи |
| Очередь задач | TaskIQ на Valkey | Нативно async, встроенный планировщик |

### Изменения к исходному техзаданию

**Better Auth убран из стека.** Это TypeScript-библиотека; при бэкенде на FastAPI её использование означало бы третий рантайм и владение пользователями вне основного приложения. Passkey реализуется через `py_webauthn`.

**Telegram-авторизация — через официальный OIDC-провайдер Telegram** (`https://oauth.telegram.org`), а не через Login Widget с проверкой хеша. Client ID и Client Secret выдаёт BotFather в разделе Bot Settings → Web Login.

**Подарочные подписки** добавлены к исходному объёму как отдельная сущность.

## 3. Декомпозиция

Восемь подпроектов. Каждый опирается только на предыдущие и имеет собственную спецификацию и план.

| # | Подпроект | Результат |
|---|---|---|
| 0 | Фундамент | `docker compose up` поднимает пустой, но работающий стек |
| 1 | Идентичность | Вход любым способом, профиль, привязки, роли, i18n |
| 2 | Подписки и Remnawave | Тарифы, синхронизация, устройства, трафик, триал |
| 3 | Деньги | YooKassa, Stars, промокоды, подарки, рефералы, выплаты |
| 4 | Коммуникации | Уведомления, win-back, тикеты, рассылки |
| 5 | Админка и метрики | Дашборд, пользователи, ноды, сопоставление подписок |
| 6 | Переработка дизайна | Внешний вид всех трёх поверхностей доведён до продажного уровня |
| 7 | Витрина | Продающий лендинг, юридические документы, подмена лендинга своим |

Этапы 0–3 — минимум, при котором проект зарабатывает. Этапы 4 и 5 добавляются поверх.

**Подпроект 6 идёт последним и не раньше.** Он не добавляет возможностей — он
переделывает то, что уже работает: лендинг, кабинет, MiniApp и админку. Пока
экраны продолжают появляться, любая доводка внешнего вида устаревает к моменту,
когда её закончили, поэтому до этого момента интерфейс делается по бренд-буку и
на компонентах `packages/ui` — достаточно хорошо, чтобы пользоваться, и без
попыток вылизать.

Работа ведётся скиллами `impeccable` и `frontend-design`; источник готовых
решений — MCP 21st.dev. Бренд-бук (`docs/design/repibot-brandbook.md`) остаётся
рамкой: подпроект вправе переосмыслить компоновку, ритм и подачу, но не цвета
знака и не зазор внутри спирали. Функциональных изменений подпроект не вносит:
контракт API и набор экранов остаются теми же, иначе переработка перестаёт быть
переработкой и превращается в отдельный подпроект.

**Подпроект 7 идёт после переработки дизайна.** Лендинга не было ни в одном из
предыдущих: до появления дизайн-системы продающую страницу пришлось бы делать
дважды. Он же закрывает юридические документы — таблица `legal_documents`
описана в разделе 5 с самого начала, но до этого момента не существовала — и
даёт разворачивающему возможность подменить главную своей страницей, не
пересобирая образы.

## 4. Структура репозитория

```
re-pibot-shop/
├── backend/                      # uv workspace
│   ├── core/                     # пакет repibot_core — вся бизнес-логика
│   │   ├── domain/               # чистые правила, без I/O
│   │   ├── db/                   # SQLAlchemy 2.0, репозитории, Alembic
│   │   ├── integrations/         # remnawave, yookassa, telegram, email
│   │   ├── services/             # сценарии
│   │   └── settings.py           # Pydantic Settings
│   ├── api/                      # FastAPI: REST + вебхуки
│   ├── bot/                      # aiogram 3.30
│   └── worker/                   # TaskIQ: крон и рассылки
├── frontend/                     # pnpm workspace
│   ├── apps/miniapp/             # React 19 + Vite 8 + TanStack Router
│   ├── apps/web/                 # Next.js 16: лендинг, юр. документы, ЛК, админка
│   └── packages/
│       ├── core/                 # openapi-fetch клиент, TanStack Query хуки, zod, i18n
│       ├── ui/                   # shadcn/ui + Radix, токены бренд-бука, Hugeicons
│       └── config/               # общие tsconfig, biome, tailwind preset
├── docker/                       # Dockerfile'ы, nginx.conf
└── docs/
```

Разделение по языкам: у бэкенда свой менеджер зависимостей (uv), у фронтенда свой (pnpm). Общего рантайма у них нет, общий контракт — OpenAPI-схема FastAPI, из которой генерируются типы для `packages/core`.

### Слои бэкенда

Зависимости направлены только вниз.

| Слой | Содержимое | Ограничение |
|---|---|---|
| `domain/` | Расчёт дней, конвертация при смене тарифа, применение промокода, реферальное начисление, правила триала | Чистые функции и dataclass'ы. Тестируется без БД и сети |
| `db/` | Модели, репозитории, миграции | Знает про Postgres, не знает про HTTP |
| `integrations/` | Внешние системы, каждая как интерфейс + реализация | Ретраи, таймауты, идемпотентность живут здесь |
| `services/` | Сценарии целиком | Единственный слой, видимый для api/bot/worker |

**Бизнес-логики нет в хендлерах aiogram и роутерах FastAPI.** Они разбирают вход, вызывают сервис, форматируют ответ. Это то, что гарантирует одинаковое поведение бота, MiniApp и веба.

### Процессы

Три отдельных Python-процесса с общей БД, общим Valkey и общим `core`:

- **api** — REST для клиентов и админки, входящие вебхуки.
- **bot** — Telegram, приём Stars, отправка уведомлений, тикеты в топиках.
- **worker** — планировщик и очередь: истечения, автоплатежи, реконсиляция, рассылки, обработка `outbox`.

Разделение нужно ради изоляции отказов: упавший бот не мешает приёму оплат, а рассылка на 5000 сообщений не блокирует ответы пользователям.

**Nginx** отдельным контейнером терминирует TLS и разводит маршруты: `/` → Next.js, `/app` → статика MiniApp, `/api` → FastAPI, `/webhook/telegram` → бот. Входящие вебхуки живут под общим префиксом `/webhook/<источник>`; `/webhook/yookassa` появится в подпроекте 3 и пойдёт в FastAPI.

## 5. Модель данных

### Разграничение истины

Наша БД владеет деньгами, тарифами, промокодами, рефералами, тикетами и личностью пользователя. Remnawave владеет доступом, трафиком, устройствами, нодами и `subscriptionUrl`. Единственная связь — `users.remnawave_id`: в панели 3.2.1 пользователь адресуется числовым идентификатором, поля `uuid` у него больше нет.

**Запись идёт только в сторону панели.** Пользователь в панели создаётся лениво, при первой выдаче подписки, с `username = rp_<id в base36>`. Трафик и список устройств запрашиваются по требованию и кэшируются в Valkey на 60 секунд; у себя мы их не дублируем.

**Вебхуки панели — источник событий, но не биллинга.** Панель шлёт `user.expired`, `user.expiration`, `user.limited`, `user.first_connected`, `user.not_connected`, `user.traffic_reset`, `user.bandwidth_usage_threshold_reached`, `user_hwid_devices.added/deleted`, `node.connection_lost/restored`. Они дают повод уведомить пользователя или админа, но никогда не двигают дату окончания — её считаем только мы.

**Реконсиляция.** Раз в настраиваемый интервал джоб сверяет `expireAt`, лимиты и состав скводов с нашей БД, приводит панель к нашему состоянию и записывает найденные расхождения в отчёт. Молчаливое исправление недопустимо: расхождение обычно означает ручную правку админом, и о ней надо знать.

### Таблицы

**Идентичность**

- `users` — `id`, `email` (уникальный, может отсутствовать), `email_verified_at`, `password_hash` (может отсутствовать), `telegram_id` (уникальный, может отсутствовать), `telegram_username`, `language`, `role` (`user`/`support`/`admin`), `status`, `referral_code`, `referred_by_id`, `remnawave_id`, `remnawave_short_uuid`, `created_at`.
- `passkey_credentials` — `user_id`, `credential_id`, `public_key`, `sign_count`, `transports`, `name`, `created_at`, `last_used_at`.
- `sessions` — `id`, `user_id`, `refresh_token_hash`, `user_agent`, `ip`, `created_at`, `expires_at`, `revoked_at`.
- `one_time_tokens` — `type` (подтверждение почты, сброс пароля, смена почты), `user_id`, `token_hash`, `payload`, `expires_at`, `used_at`.
- `trial_grants` — `telegram_id` (первичный ключ), `granted_at`, `user_id`.

`trial_grants` живёт отдельно от `users` и не удаляется каскадом. Флаг на самом пользователе обходится удалением аккаунта и повторной регистрацией.

**Подписки**

- `plans` — `id`, `code`, `name` (по локалям), `description`, `duration_days`, `price_rub`, `price_stars`, `traffic_limit_bytes`, `traffic_reset_strategy`, `hwid_device_limit`, `internal_squad_uuids`, `is_active`, `is_visible`, `sort_order`.
- `subscriptions` — `user_id` (уникальный), `plan_id`, `status` (`trial`/`active`/`expired`/`disabled`/`pending_provision`), `started_at`, `expires_at`, `auto_renew_enabled`, `payment_method_id`, `source`, `updated_at`.
- `subscription_events` — журнал: `user_id`, `type` (покупка, продление, смена тарифа, бонусные дни, подарок, действие админа), `days_delta`, `plan_id`, `payment_id`, `actor`, `comment`, `created_at`.

Текущее состояние читается одним запросом, полная история начислений доступна для разбора спорных случаев.

**Деньги**

- `payments` — `id`, `user_id`, `provider` (`yookassa`/`stars`), `provider_payment_id`, `idempotence_key`, `amount_rub`, `amount_stars`, `status` (`pending`/`succeeded`/`canceled`/`refunded`), `purpose` (`purchase`/`renew`/`gift`), `plan_id`, `promo_code_id`, `discount_amount`, `save_payment_method`, `receipt_payload` (не заполняется, пока фискализация выключена), `created_at`, `paid_at`, `raw_payload`.
- `payment_methods` — `user_id`, `provider_method_id`, `title`, `is_default`, `created_at`.
- `promo_codes` — `code`, `type` (`percent`/`fixed_rub`/`bonus_days`), `value`, `max_uses`, `used_count`, `per_user_limit`, `valid_from`, `valid_until`, `applicable_plan_ids`, `is_active`, `created_by`.
- `promo_redemptions` — `promo_code_id`, `user_id`, `payment_id`, `redeemed_at`.
- `gift_vouchers` — `code`, `plan_id`, `purchased_by_user_id`, `payment_id`, `redeemed_by_user_id`, `redeemed_at`, `expires_at`, `status`.
- `referrals` — `referrer_id`, `referee_id`, `created_at`, `rewarded_at`, `reward_transaction_id`.
- `balance_transactions` — `user_id`, `amount_rub`, `type` (`referral_reward`/`converted_to_days`/`payout`/`adjustment`), `related_id`, `balance_after`, `created_at`.
- `payout_requests` — `user_id`, `amount_rub`, `card_details_encrypted`, `status` (`pending`/`paid`/`rejected`), `processed_by`, `processed_at`, `comment`.

**Коммуникации**

- `tickets` — `user_id`, `subject`, `status` (`open`/`answered`/`closed`), `tg_topic_id`, `created_at`, `last_message_at`.
- `ticket_messages` — `ticket_id`, `author` (`user`/`staff`), `staff_user_id`, `text`, `attachments`, `tg_message_id`, `created_at`.
- `notifications_log` — `user_id`, `type`, `channel` (`telegram`/`email`), `dedup_key` (уникальный), `sent_at`.
- `broadcasts` — `channel`, `audience_filter`, `message` (по локалям), `status`, `scheduled_at`, `started_at`, `finished_at`, `created_by`, `stats`.
- `broadcast_recipients` — `broadcast_id`, `user_id`, `status`, `error`, `sent_at`.

**Служебное**

- `outbox` — `topic`, `payload`, `available_at`, `attempts`, `last_error`, `processed_at`.
- `webhook_events` — `source`, `event_id`, `event`, `payload`, `received_at`, `processed_at`.
- `audit_log` — `actor_id`, `action`, `entity`, `entity_id`, `before`, `after`, `ip`, `created_at`.
- `legal_documents` — `slug`, `locale`, `title`, `content`, `version`, `published_at`, `created_by_id`.

`outbox` решает конкретную задачу: оплата прошла, панель в этот момент недоступна. Платёж переводится в `succeeded`, подписка в `pending_provision` в одной транзакции, задача выдачи доступа ретраится до успеха, пользователь видит «активируем, обычно до минуты». Без этого выбор стоял бы между потерей оплаченных подписок и списанием денег без выдачи доступа.

## 6. Ключевые потоки

### Покупка картой

1. Клиент вызывает `POST /api/payments` с тарифом и, при наличии, промокодом.
2. Сервис проверяет тариф, применяет скидку, создаёт `payments` в статусе `pending` со своим ключом идемпотентности, вызывает YooKassa и возвращает `confirmation_url`.
3. Вебхук YooKassa **не принимается на веру**: проверяется источник и перезапрашивается платёж через API со сверкой суммы и статуса.
4. В одной транзакции: платёж в `succeeded`, начисление дней, запись в `subscription_events`, погашение промокода, реферальное начисление при первой оплате, три задачи в `outbox` — выдать доступ в панели, уведомить пользователя, уведомить админ-группу.
5. Воркер разбирает `outbox`.

Если вебхук не дошёл, крон добирает `pending`-платежи старше пяти минут опросом API YooKassa. Обе дороги ведут в одну функцию финализации, повторное начисление исключено ключом идемпотентности.

### Оплата звёздами

`sendInvoice` в валюте XTR с uuid платежа в payload. На `pre_checkout_query` проверяется, что платёж жив и тариф активен. На `successful_payment` вызывается та же функция финализации, что и для карты. Возврат — `refundStarPayment` из админки.

### Начисление дней

Продление тем же тарифом сдвигает `expires_at` от текущей даты окончания, если подписка активна, и от текущего момента, если истекла.

Смена тарифа при активной подписке: остаток пересчитывается в деньги по стоимости дня текущего тарифа и конвертируется в дни нового. Возвраты не нужны, оплаченное не теряется. Поведение выносится в настройку — альтернатива — заменить тариф с потерей остатка.

### Автоплатёж

За сутки до окончания крон списывает по сохранённому методу оплаты. Неудача — уведомление и ещё две попытки с интервалом в сутки, после чего автопродление выключается и пользователь получает обычное уведомление об истечении.

### Триал

Требует привязанного Telegram. Проверка по `trial_grants` — по `telegram_id`, а не по аккаунту.

### Подарок

Оплата с `purpose=gift` порождает ваучер с кодом и сроком жизни. Покупателю приходит код и ссылка `t.me/<bot>?start=gift_XXX`. Активирует тот, кто первым перешёл. При активной подписке у получателя дни прибавляются по тому же правилу конвертации.

### Возврат ушедшего пользователя

Лесенка после истечения: на следующий день напоминание, на третий — персональный промокод со скидкой и коротким сроком, через две недели — несколько бесплатных дней в одну кнопку, через месяц — последнее касание. Пороги и размеры задаются конфигурацией.

### Уведомления

Базовый набор: приближение окончания подписки (за три дня, за день и в день истечения), факт истечения, успешная оплата, неоплаченный счёт — если платёж остаётся в `pending` дольше получаса, пользователю уходит одно напоминание со ссылкой на оплату.

Все уведомления дедуплицируются ключом в `notifications_log`. Для истечения ключ — `{user}:{тип}:{дата окончания}`, для счёта — `{user}:{тип}:{платёж}`. Перезапуск воркера, повторный крон и ретрай задачи не приводят к повторной отправке.

Канал выбирается по доступности: Telegram, если он привязан, иначе почта. Дублирование в оба канала одного и того же события не делается.

### Тикеты

Обращение создаёт топик в супергруппе. Ответ сотрудника в топике бот пересылает пользователю, всё сохраняется в `ticket_messages` и отображается в админке. Закрытие — командой в топике или из админки. Отдельные топики отведены под регистрации, оплаты и алерты нод.

## 7. Авторизация и безопасность

### Схемы токенов

**Браузер.** Вход по email с паролем, Passkey или Telegram OIDC выдаёт короткий access-токен в теле ответа и refresh в httpOnly Secure cookie. Refresh хранится в `sessions`, отзывается по одному и списком, у каждой сессии видны устройство и IP.

**MiniApp.** Refresh не используется. Telegram при каждом открытии выдаёт свежий `initData`, который обменивается на access-токен, хранимый только в памяти JS. В веб-версии Telegram наш домен оказывается в стороннем контексте, где cookie не переживут; кроме того, ничего чувствительного не попадает в `localStorage`.

Cookie видит ровно один эндпоинт — `/auth/refresh`. Всё остальное API принимает только заголовок `Authorization`. Поверхность CSRF сводится к одному методу, закрываемому `SameSite` и проверкой `Origin`.

### Способы входа

| Способ | Проверка |
|---|---|
| Пароль | argon2id, одинаковый ответ на неизвестный email и неверный пароль, задержка и блокировка после серии попыток |
| Passkey | WebAuthn через `py_webauthn`, discoverable credentials, счётчик подписей |
| Telegram (браузер) | OIDC: authorization code + PKCE (S256), issuer `https://oauth.telegram.org`, валидация ID-токена по JWKS, scope `openid profile telegram:bot_access` |
| Telegram (MiniApp) | HMAC от `initData` на токене бота, `auth_date` не старше суток |

Scope `telegram:bot_access` даёт боту право писать пользователю первым. Без него человек, зарегистрировавшийся на сайте через Telegram, не получил бы уведомлений об истечении и оплате. Scope `phone` не запрашивается: телефон не нужен, а хранение его — лишняя ответственность.

`client_id` и `client_secret` из BotFather задаются переменными окружения. Redirect URI и Trusted Origins прописываются в BotFather под каждый домен развёртывания; это входит в инструкцию по установке.

### Привязка и отвязка

Привязка второго способа входа — отдельная операция с подтверждением, а не побочный эффект входа. Отвязка Telegram запрещена, если это единственный способ войти. То же с удалением последнего passkey при отсутствующем пароле.

### Входящие вебхуки

Все входящие вебхуки приходят на постоянные пути `/webhook/<источник>`. Секретов в адресе нет: URL целиком попадает в журналы прокси и мониторинга, поэтому источник подтверждается заголовком, подписью или перезапросом, но не знанием пути. Telegram — заголовок `X-Telegram-Bot-Api-Secret-Token`. YooKassa — проверка источника и перезапрос платежа через API. Remnawave — HMAC-подпись из заголовка, имя заголовка и секрет берутся из конфигурации панели. Оба источника пишутся в `webhook_events` и обрабатываются идемпотентно: для Remnawave ключом служит пара события и его отметки времени, для YooKassa — пара идентификатора платежа и статуса, поскольку собственного идентификатора события провайдер не присылает.

### Разграничение доступа

Роли проверяются на бэкенде. Клиентские и админские маршруты разведены (`/api/*` и `/api/admin/*`). Роль `support` не имеет доступа к тарифам, рассылкам, нодам и выплатам. Каждое действие персонала пишется в `audit_log` с состоянием до и после.

Реквизиты карт для реферальных выплат шифруются на уровне приложения ключом из окружения, доступны только роли `admin`, факт просмотра логируется. Это единственные чувствительные данные, которые хранятся у нас: карточные данные покупателей проходят через YooKassa и до нас не доходят.

Лимиты запросов на `/auth/*`, создание платежей, отправку писем и создание тикетов — по IP и по пользователю, на Valkey.

## 8. Тестирование

| Уровень | Инструмент | Что покрывается |
|---|---|---|
| Домен | pytest | Расчёт дней, конвертация при смене тарифа, промокоды, правила триала — без БД и сети |
| Сервисы | pytest + testcontainers (Postgres) | Сценарии целиком с заглушками на YooKassa и Remnawave |
| Вебхуки | pytest | Повторная доставка, битая подпись, гонка вебхука и крона |
| Фронтенд | Vitest | Логика и хуки из `packages/core` |
| Сквозные | Playwright | Регистрация → триал → подключение; покупка → оплата → доступ |

Ruff и mypy в strict, Biome и TypeScript 6 strict — блокирующие проверки в CI.

## 9. Развёртывание

Multi-stage сборки: Python-образы на базе `uv` с отдельным слоем зависимостей, MiniApp собирается в статику, Next.js — в standalone-сборку. Один `compose.yml` и оверлей для варианта с панелью Remnawave на том же сервере. Nginx отдельным контейнером с TLS и заголовками безопасности. Миграции Alembic выполняются отдельным одноразовым сервисом до старта API, чтобы три процесса не конкурировали за блокировку.

## 10. Вне области

Не входит в базовую версию и не проектируется заранее:

- Платёжные провайдеры кроме YooKassa и Telegram Stars.
- Криптовалютные платежи.
- Мобильные приложения.
- Партнёрская программа сложнее фиксированной награды за первую оплату.
- Автоматические выплаты рефералам: выплаты остаются ручными.
- Мультивалютность: расчёты только в рублях и звёздах.
- Мультитенантность: одно развёртывание обслуживает одну панель.
