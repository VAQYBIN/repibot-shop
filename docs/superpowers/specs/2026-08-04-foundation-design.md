## 1. Цель

Собрать каркас, на который встают все пять последующих подпроектов. Бизнес-функций здесь нет намеренно: тарифов, оплат и подписок в этом этапе не появляется.

**Критерий готовности:** на чистой машине `docker compose up` поднимает работающий стек, а `uv run check` проходит все проверки без единой ошибки.

Скучный результат — правильный результат. Кривая конфигурация или несобирающийся образ, пропущенные здесь, всплывут в каждом следующем этапе.

## 2. Состав развёртывания

| Сервис | Образ | Назначение |
|---|---|---|
| `nginx` | nginx:alpine | TLS, маршрутизация, заголовки безопасности |
| `web` | multi-stage Node | Next.js 16, standalone-сборка |
| `api` | multi-stage Python | FastAPI |
| `bot` | тот же образ, другая команда | aiogram |
| `worker` | тот же образ, другая команда | TaskIQ + планировщик |
| `migrate` | тот же образ, одноразовый | Alembic, отрабатывает до старта `api` |
| `postgres` | postgres:18-alpine | Основное хранилище |
| `valkey` | valkey/valkey:alpine | Кэш и очередь |

Три Python-процесса используют один образ и различаются только командой запуска. Пересборка одна, поведение предсказуемое.

MiniApp отдельным сервисом не выделяется: это набор статических файлов, и он собирается первой стадией образа `nginx`. Контейнер, единственная задача которого — держать том с готовой статикой, ничего не даёт, но добавляет ещё одну единицу в вывод `docker compose ps`.

`migrate` завершается успехом до того, как стартуют `api`, `bot` и `worker` (`depends_on` с условием `service_completed_successfully`). Это снимает конкуренцию трёх процессов за блокировку миграций.

Два compose-файла: `compose.yml` для варианта с внешней панелью Remnawave и `compose.local-panel.yml` — оверлей, подключающий сеть панели, развёрнутой на том же сервере.

### Маршрутизация Nginx

| Путь | Назначение |
|---|---|
| `/` | Next.js |
| `/app` | Статика MiniApp, SPA-fallback на `index.html` |
| `/api` | FastAPI |
| `/webhook/telegram` | Бот |

Входящие вебхуки собраны под общим префиксом `/webhook/<источник>`: в подпроекте 3 к ним добавится `/webhook/yookassa`, уже на стороне `api`. Пути постоянные и несекретные — URL целиком пишется в журнал доступа и в любой промежуточный прокси. Подлинность запроса Telegram подтверждает заголовок `X-Telegram-Bot-Api-Secret-Token`.

Заголовки: HSTS, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` для веба. Для `/app` вместо `X-Frame-Options` — CSP с `frame-ancestors`, разрешающим домены Telegram: MiniApp обязан открываться во фрейме.

## 3. Бэкенд

### Рабочее пространство

`uv` workspace с четырьмя пакетами: `core`, `api`, `bot`, `worker`. Три последних зависят от `core` и содержат минимум кода — точку входа и композицию.

Python 3.13. Зависимости фиксируются в `uv.lock` и коммитятся.

### `repibot_core`

В этом этапе наполняются:

- **`settings.py`** — Pydantic Settings: строка подключения к БД, Valkey, токен бота и его вебхук-секрет, адрес и токен панели Remnawave, ключи YooKassa, SMTP, ключ подписи JWT, ключ шифрования, домены, языки. Обязательные переменные без значения по умолчанию валятся при старте с внятным сообщением, а не при первом обращении.
- **`db/`** — асинхронный движок SQLAlchemy 2.0, фабрика сессий, декларативная база с общими примесями (`id`, `created_at`, `updated_at`), настроенный Alembic и первая миграция — таблица `users` в минимальном виде (`id`, `created_at`), достаточная для проверки работоспособности цепочки.
- **`integrations/remnawave/models.py`** — Pydantic-модели, сгенерированные из `docs/remnawave-api/api-1.json`, и заготовка клиента с базовым URL, токеном, таймаутами и ретраями. Ни одного бизнес-метода — они появятся в подпроекте 2.
- **`logging.py`** — структурные логи в JSON, идентификатор запроса сквозным контекстом, фильтр, вырезающий токены и секреты из сообщений.

Слои `domain/` и `services/` создаются пустыми с описанием назначения в `__init__.py`.

### `api`

FastAPI с `/health` (проверяет доступность Postgres и Valkey и отвечает раздельным статусом по каждому) и `/openapi.json`. Настроены CORS, middleware идентификатора запроса, единый обработчик ошибок. Роутеры разведены по префиксам `/api` и `/api/admin` — пока пустые.

Проверка живости ограничена по времени: зависшая зависимость считается упавшей, иначе наблюдатель вместо «база недоступна» получает таймаут собственного запроса. Движок создаётся один раз на процесс. Оба исхода, `200` и `503`, описаны в схеме — клиент генерирует типы из неё, и неописанный ответ для него не существует.

Список источников CORS собирается из `PUBLIC_WEB_URL` и `PUBLIC_APP_URL` приведением к origin: браузер присылает в `Origin` только схему, хост и порт, и запись с путём (`/app`) не совпала бы ни с одним запросом.

**Единый формат ошибок** распространяется на все ответы, включая те, что порождает сам фреймворк:

```json
{"error": {"code": "not_found", "message": "..."}}
```

Ошибки проверки данных добавляют поле `details` со списком `{loc, msg}` — без него форма не покажет, что именно неверно. Значение поля туда не попадает: в нём приходит то, что прислал клиент, вплоть до пароля из формы входа.

Идентификатор запроса ставится в самом обработчике ошибки, а не только в middleware: ответ `500` собирает `ServerErrorMiddleware`, который стоит снаружи пользовательских middleware, и обратно через них ответ уже не проходит.

### `bot`

aiogram 3.30 на вебхуках: приложение отдаёт эндпоинт на постоянном пути `/webhook/telegram`, Nginx проксирует его в контейнер бота. Запрос без верного заголовка `X-Telegram-Bot-Api-Secret-Token` получает 401. Обработчик `/start` отвечает заглушкой. Настроены диспетчер, хранилище состояний на Valkey и middleware с логированием.

Режим long polling добавляется переменной окружения — он нужен для локальной разработки, где внешний вебхук недоступен.

### `worker`

TaskIQ с брокером на Valkey и планировщиком. Одна задача-заглушка по расписанию, пишущая в лог, — она подтверждает, что и очередь, и планировщик, и подключение к БД из воркера работают.

## 4. Фронтенд

### Рабочее пространство

`pnpm` workspace: `apps/miniapp`, `apps/web`, `packages/core`, `packages/ui`, `packages/config`. TypeScript 6 в strict, Biome для форматирования и линтинга во всех пакетах.

### `packages/config`

Базовый `tsconfig`, конфигурация Biome, пресет Tailwind v4 с токенами бренда. Всё остальное наследуется отсюда — расхождение настроек между приложениями исключается на уровне структуры.

### `packages/ui`

Токены бренд-бука переносятся в Tailwind v4 через `@theme` — светлая тема в `:root`, тёмная в `[data-theme="dark"]`, ровно теми значениями, что заданы в бренд-буке.

Компоненты shadcn/ui поверх Radix, настроенные на эти токены. В этом этапе создаётся минимум: кнопка, поле ввода, карточка — достаточно, чтобы проверить, что тема, тёмный режим и фокус работают. Иконки — Hugeicons.

Шрифты Inter и JetBrains Mono подключаются локально, а не с внешнего CDN: у проекта аудитория, для которой обращение к стороннему домену на каждой загрузке страницы нежелательно.

Правила бренд-бука, которые проверяются глазами на демо-странице: фокус всегда видим и акцентного цвета; в тёмной теме используется Jade Bright, а не основной Jade; мелкий текст на зелёном — тёмный, а не белый.

### `packages/core`

Клиент к нашему API на `openapi-fetch` с типами, сгенерированными `openapi-typescript` из `/openapi.json` FastAPI. Провайдер TanStack Query v5 с общими настройками повторов и времени жизни кэша. Каркас i18n с русским и английским словарями и определением языка. Zod-схемы для форм.

Сгенерированные типы коммитятся в репозиторий: сборка фронтенда не должна требовать поднятого бэкенда. Расхождение ловится отдельной проверкой в CI, которая перегенерирует типы и падает, если результат отличается от закоммиченного.

### `apps/miniapp`

React 19, Vite 8, TanStack Router, Zustand. Инициализация Telegram WebApp SDK, применение темы Telegram поверх токенов бренда, одна страница с приветствием и переключателем языка. Сборка — статика в `dist`.

### `apps/web`

Next.js 16, App Router. Главная страница с вордмарком и переключателем темы, маршрут `/legal/[slug]` с заглушкой. Раздел `/admin` создаётся как отдельный сегмент со своим макетом — пустой.

## 5. Логотип

В `docs/design/` есть четыре растровых файла с альфа-каналом:

| Файл | Размер | Что это |
|---|---|---|
| `logo-light.png` | 150×150 | Плашка: знак вывороткой на заливке Jade |
| `logo-dark.png` | 150×150 | Плашка: знак на заливке Ink, ядро в Jade Bright |
| `lock-up-dark.png` | 350×150 | Горизонтальный лок-ап, знак в Ink — для светлого фона |
| `lock-up-light.png` | 350×150 | Горизонтальный лок-ап целиком в Jade — одноцветная версия |

**Используется в этапе 0:** плашки как аватарка бота, favicon и знак в шапке. Разрешения для этого достаточно.

Лок-ап в шапке собирается из плашки и текстового вордмарка, а не берётся готовым растром. Причина в том, что готового лок-апа для тёмной темы не существует: `lock-up-dark.png` рассчитан на светлый фон, а `lock-up-light.png` целиком в Jade и на тёмном даёт мутное пятно. Текстовый вордмарк снимает вопрос — он наследует цвет темы, двоеточие остаётся акцентным в обоих случаях, а просвет до знака задаётся в `em` и потому не ломается при масштабировании.

**Ограничения, которые надо знать заранее.** Файлы растровые, максимум 150 px по меньшей стороне. Из них нельзя получить `og-image.png` 1200×630 и иконки PWA 512 и 192 — апскейл даст замыленный край на скруглениях. Фирменный прелоадер из раздела 6 бренд-бука — вращение спирали при неподвижном ядре — на растре не реализуется вовсе: спираль и ядро должны быть отдельными элементами SVG. Упрощённой версии для 16–32 px нет, а бренд-бук прямо предупреждает, что уменьшением исходника это не решается.

**`lock-up-light.png` не годится как лок-ап на светлом фоне.** Вордмарк в нём целиком выкрашен в Jade, тогда как раздел 5 бренд-бука требует буквы в Ink и только двоеточие в Jade, а раздел 7 даёт Jade на Paper контраст 3.1:1 — ниже порога для текста. Файл остаётся как одноцветная версия для тиснения и гравировки. На светлой теме используется `lock-up-dark.png`.

**Именование выравнивается при переносе в код.** Суффикс всегда означает тему интерфейса, для которой файл предназначен, а не цвет знака: сегодняшний `lock-up-dark.png` становится лок-апом светлой темы. Иначе подстановка не того файла — вопрос времени.

**Вне этого этапа:** перевод знака в вектор, упрощённая версия для малых размеров, вертикальный лок-ап, прелоадер, `og-image` и иконки PWA. До публичного запуска это нужно закрыть; ссылки на файлы закладываются так, чтобы подстановка готовых SVG не требовала правки разметки.

## 6. Проверки и CI

Единая команда проверки локально и один workflow в CI выполняют одно и то же.

Команда реализуется кроссплатформенно — скриптом на Python, запускаемым через `uv run check`, а не Makefile: основная машина разработки работает под Windows, где `make` не установлен по умолчанию, а CI — под Linux. Один и тот же вход в обоих окружениях означает, что «у меня локально проходило» перестаёт быть возможным объяснением.

Состав проверок:

| Проверка | Команда |
|---|---|
| Линт Python | `ruff check`, `ruff format --check` |
| Типы Python | `mypy` в strict |
| Тесты Python | `pytest` |
| Линт фронтенда | `biome ci` |
| Типы фронтенда | `tsc --noEmit` во всех пакетах |
| Тесты фронтенда | `vitest run` |
| Синхронность типов API | Перегенерация и сравнение с закоммиченным |
| Сборка | `docker compose build` |

Тесты этапа: `/health` отвечает и корректно определяет недоступность Postgres; настройки падают при отсутствии обязательной переменной; миграции применяются на чистой БД и откатываются; задача воркера ставится в очередь и выполняется; `/start` отвечает; главные страницы обоих фронтендов рендерятся.

Playwright настраивается, но сценариев пока не содержит — они появятся в подпроекте 1, когда будет что проверять.

## 8. Критерии приёмки

1. `docker compose up` на чистой машине поднимает все сервисы, `api` отвечает на `/health` полным успехом.
2. Бот отвечает на `/start` через вебхук за Nginx.
3. Задача воркера выполняется по расписанию и видна в логах.
4. Обе фронтенд-страницы открываются, переключение светлой и тёмной темы работает, цвета совпадают с бренд-буком.
5. MiniApp открывается внутри Telegram и получает `initData` (без обмена на токен — это подпроект 1).
6. `uv run check` проходит полностью и на Windows, и на Linux.
7. Отсутствие обязательной переменной окружения приводит к падению при старте с указанием, какой именно переменной не хватает.
8. Повторный `docker compose up` не пытается применить миграции заново.

## 9. Вне области

Аутентификация, тарифы, платежи, любые вызовы бизнес-методов панели Remnawave, отправка писем, реальные экраны. Всё это — последующие подпроекты.
