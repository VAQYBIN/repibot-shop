## 1. Цель

Дать пользователю аккаунт, а системе — понятие «кто это». После этого подпроекта
человек входит в веб-кабинет и в MiniApp, управляет способами входа и языком,
а бэкенд умеет отличать клиента от сотрудника и от админа.

**Критерий готовности:** на чистом развёртывании можно зарегистрироваться по
почте, подтвердить адрес письмом, войти в кабинет, привязать Telegram, войти
через него повторно и отозвать сессию — и `uv run check` проходит целиком.

Подписок, тарифов и оплат здесь по-прежнему нет. Появляется только то, без чего
их не к чему привязать.

Работа разбита на два плана: **1a** — ядро (пароль, почта, сессии, MiniApp,
роли), **1b** — остальные способы входа (passkey, Telegram OIDC, привязки).
После каждого плана результат работает руками и проверки зелёные.

## 2. Модель данных

### `users`

Таблица дорастает от каркаса подпроекта 0 до состава, заданного архитектурой:

| Поле | Тип | Замечание |
|---|---|---|
| `email` | `varchar`, уникальный, `null` | Хранится в нижнем регистре, нормализуется до записи |
| `email_verified_at` | `timestamptz`, `null` | Пока пусто — входа нет |
| `password_hash` | `varchar`, `null` | Argon2id. Пусто у тех, кто вошёл только через Telegram |
| `telegram_id` | `bigint`, уникальный, `null` | Идентификатор Telegram не влезает в `integer` |
| `telegram_username` | `varchar`, `null` | Меняется на стороне Telegram, обновляется при каждом входе |
| `name` | `varchar`, `null` | Отображаемое имя, редактируется в профиле |
| `language` | `varchar(2)` | `ru` или `en`, не `null` |
| `role` | `enum` | `user` / `support` / `admin` |
| `status` | `enum` | `active` / `banned` |
| `referral_code` | `varchar`, уникальный | Генерируется при создании пользователя |
| `referred_by_id` | FK на `users`, `null` | Заполняется в подпроекте 3 |
| `remnawave_id` | `bigint`, `null` | Заполняется в подпроекте 2. Заводилось как `remnawave_uuid`; панель 3.2.1 адресует пользователя числом, поле заменено |
| `remnawave_short_uuid` | `varchar`, `null` | То же |

Аккаунт существует, если у него есть хотя бы один способ входа: подтверждённая
почта с паролем, passkey или привязанный Telegram. Оба поля почты и пароля
допускают `null`, потому что вход через Telegram не требует ни того, ни другого.

`referral_code` и `referred_by_id` заводятся сразу, хотя награды считаются
только в подпроекте 3: добавить два поля в пустую таблицу дешевле, чем
миграцию к таблице с пользователями. Захват реферальных ссылок в область этого
подпроекта не входит.

### Новые таблицы

- **`sessions`** — `id`, `user_id`, `refresh_token_hash`, `previous_token_hash`,
  `rotated_at`, `user_agent`, `ip`, `created_at`, `expires_at`, `revoked_at`.
- **`passkey_credentials`** — `user_id`, `credential_id` (уникальный),
  `public_key`, `sign_count`, `transports`, `name`, `created_at`, `last_used_at`.
- **`one_time_tokens`** — `type` (`email_verify` / `password_reset` /
  `email_change`), `user_id`, `token_hash` (уникальный), `payload`, `expires_at`,
  `used_at`.
- **`audit_log`** — `actor_id`, `action`, `entity`, `entity_id`, `before`,
  `after`, `ip`, `created_at`.
- **`outbox`** — `topic`, `payload`, `available_at`, `attempts`, `last_error`,
  `processed_at`.

`trial_grants` в этом подпроекте не создаётся: триал — подпроект 2.

### Зачем `outbox` уже здесь

Верификация почты жёсткая: без подтверждённого адреса входа нет. Значит
недоставленное письмо — это потерянная регистрация, а не неудобство.
Пользователь и задача на письмо пишутся в одной транзакции, воркер разбирает
очередь с экспоненциальной задержкой и хранит последнюю ошибку. Тот же механизм
в подпроекте 3 будет выдавать доступ в панели после оплаты, поэтому строится он
один раз и сразу правильно.

Отдельная кнопка «отправить письмо снова» в интерфейсе всё равно нужна:
почтовый адрес может оказаться с опечаткой, и никакие ретраи это не исправят.

## 3. Сессии и токены

| Токен | Форма | Срок | Где живёт |
|---|---|---|---|
| Access | JWT HS256 на `JWT_SECRET`, claims `sub`, `sid`, `exp` | 15 минут | Память JS, заголовок `Authorization` |
| Refresh | 256 бит случайности, непрозрачный | 30 дней | httpOnly Secure cookie, в БД только `sha256` |

**Роли в токене нет.** Роль и статус читаются из БД по первичному ключу с кэшем
в Valkey на 30 секунд. Положи роль в access-токен — и блокировка пользователя
начнёт действовать через 15 минут вместо мгновенной.

**Ротация.** Каждый обмен выдаёт новую пару. Прежний хеш переносится в
`previous_token_hash` вместе с `rotated_at`. Приход прежнего токена в течение
30 секунд после ротации считается гонкой вкладок и обслуживается новой парой;
позже — признаком утечки, и вся сессия отзывается.

Без окна две открытые вкладки, одновременно обновившие токен, выкидывали бы
пользователя из системы. Без отзыва украденный refresh работал бы месяц.

**Cookie видит ровно один эндпоинт** — `POST /api/auth/refresh`, он же проверяет
`Origin`. Остальное API принимает только заголовок `Authorization`, и поверхность
CSRF сводится к одному методу.

**MiniApp refresh не получает.** Истёк access — фронтенд обменивает свежий
`initData`, который Telegram отдаёт при каждом открытии. В веб-версии Telegram
наш домен оказывается в стороннем контексте, где cookie не выживет.

## 4. Слои и состав кода

### `domain/`

Чистые правила, тестируются без БД и сети:

- нормализация почты и проверка формата;
- политика пароля: не короче 10 символов, не совпадает с адресом почты;
- сроки жизни одноразовых токенов по типу: подтверждение почты — 24 часа,
  сброс пароля — 1 час, смена почты — 1 час, код привязки Telegram — 10 минут;
- генерация реферального кода и кода привязки: алфавит без похожих символов;
- `can_unlink(state, method)` — можно ли снять способ входа. Отвязка Telegram
  запрещена, если это единственный вход; удаление последнего passkey запрещено
  при отсутствующем пароле.

### `services/auth/`

`AuthService` с единственным путём выдачи сессии и четырьмя верификаторами:

| Верификатор | Проверка |
|---|---|
| `password` | Argon2id, единый ответ на неизвестный адрес и неверный пароль |
| `passkey` | WebAuthn через `py_webauthn`, discoverable credentials, счётчик подписей |
| `telegram_oidc` | Authorization Code + PKCE S256, валидация ID-токена по JWKS |
| `telegram_initdata` | HMAC от `initData` на токене бота, `auth_date` не старше суток |

Каждый возвращает `VerifiedIdentity`; дальше общий код находит или создаёт
пользователя, проверяет статус, пишет в `audit_log` и выдаёт сессию. Пятый
способ входа не трогает выдачу токенов, и «в одном месте проверили статус, в
трёх забыли» становится невозможным.

RP ID для WebAuthn выводится из `PUBLIC_WEB_URL`, отдельной переменной не
получает: разойтись эти значения не должны.

### `integrations/email/`

Интерфейс `EmailSender` и две реализации: SMTP и запись в лог. Шаблоны на
Jinja2, по два на письмо (текст и HTML), на русском и английском, в цветах
бренд-бука. Каждый разворачивающий подключит свой SMTP; лог-реализация
существует для тестов.

### `integrations/telegram/`

Клиент Bot API для того, что нужно вне процесса бота: `getMe` для сборки
`t.me`-ссылки привязки, с кэшем в Valkey.

## 5. API

Все пути под `/api`. Ошибки — в едином формате подпроекта 0, с кодами:
`invalid_credentials`, `email_not_verified`, `email_taken`, `weak_password`,
`token_invalid`, `token_expired`, `rate_limited`, `last_login_method`,
`telegram_already_linked`, `link_conflict`, `unauthorized`, `forbidden`.

**Тексты ошибок API не локализует.** Он возвращает код, фразу подбирает
фронтенд из своих словарей. Локализуются на бэкенде только письма и сообщения
бота — там нет клиента, который мог бы это сделать.

### Публичные

| Метод и путь | Что делает |
|---|---|
| `POST /auth/register` | Создаёт пользователя без права входа, ставит письмо в `outbox` |
| `POST /auth/verify-email` | Подтверждает адрес и сразу выдаёт сессию |
| `POST /auth/resend-verification` | Повторное письмо, ответ всегда одинаковый |
| `POST /auth/login` | Пароль. Неподтверждённый адрес — `email_not_verified` |
| `POST /auth/refresh` | Единственный, кто читает cookie, проверяет `Origin` |
| `POST /auth/logout` | Отзывает текущую сессию, гасит cookie |
| `POST /auth/password/forgot` | Ответ одинаковый независимо от существования адреса |
| `POST /auth/password/reset` | Отзывает все сессии и выдаёт новую |
| `POST /auth/passkey/login/options` | Challenge в Valkey на 5 минут |
| `POST /auth/passkey/login/verify` | Проверка ответа аутентификатора, сессия |
| `GET /auth/telegram/start` | Редирект на `oauth.telegram.org/auth`, `state` и `code_verifier` в Valkey |
| `GET /auth/telegram/callback` | Обмен кода, проверка ID-токена, сессия, редирект в кабинет |
| `POST /auth/telegram/miniapp` | Обмен `initData` на access-токен без refresh |

Telegram-вход в браузере — полный редирект, а не всплывающее окно: тогда
`Cross-Origin-Opener-Policy` из фундамента не приходится ослаблять.

Scope запрашивается `openid profile telegram:bot_access`. Последний даёт боту
право написать пользователю первым — без него зарегистрировавшийся на сайте не
получил бы ни одного уведомления. Scope `phone` не запрашивается: телефон не
нужен, а хранение его — ответственность без выгоды.

### Приватные

| Метод и путь | Что делает |
|---|---|
| `GET /me` | Профиль, роль, язык, список привязанных способов входа |
| `PATCH /me` | Имя и язык |
| `POST /me/email/change-request` | Письмо на новый адрес; для аккаунта без почты это её добавление |
| `POST /me/email/change-confirm` | Подтверждение по токену из письма |
| `POST /me/password` | Установка или смена. Текущий пароль требуется, если он был |
| `GET /me/sessions` | Список с устройством, адресом и датой |
| `DELETE /me/sessions/{id}` | Отзыв одной |
| `DELETE /me/sessions` | Отзыв всех, кроме текущей |
| `POST /me/passkeys/options` | Параметры регистрации ключа |
| `POST /me/passkeys` | Сохранение ключа с именем |
| `GET /me/passkeys`, `DELETE /me/passkeys/{id}` | Список и удаление по правилу `can_unlink` |
| `POST /me/telegram/link-code` | Код и ссылка `t.me/<bot>?start=link_XXX` |
| `DELETE /me/telegram` | Отвязка по правилу `can_unlink` |
| `GET /admin/whoami` | Гейт роли; страницы админки — подпроект 5 |

### Привязка Telegram и дубли

Вход через Telegram с незнакомым идентификатором создаёт новый аккаунт. Тихого
слияния нет: при захвате Telegram-аккаунта оно отдало бы чужие подписки.

Кабинет выдаёт код, бот принимает его командой `/start link_XXX`:

| Состояние Telegram-аккаунта | Результат |
|---|---|
| Не встречался | Привязывается к аккаунту, выдавшему код |
| Есть аккаунт без почты, пароля и passkey | Пустой дубль поглощается, привязка проходит |
| У аккаунта есть свой способ входа | Отказ `link_conflict` с объяснением |

Поглощение пустого дубля закрывает основной сценарий: человек открыл MiniApp,
потом зарегистрировался на сайте и хочет один аккаунт. Отказ во втором случае
принципиален — в подпроекте 3 у каждого аккаунта появятся деньги, и склеивать
их автоматически нельзя.

## 6. Роли

`ADMIN_TELEGRAM_IDS` — список идентификаторов в окружении. При входе такого
пользователя роль поднимается до `admin`, событие пишется в `audit_log`.
Владелец панели свой Telegram ID знает, и пароль для первого входа выдумывать
не нужно.

Удаление идентификатора из переменной роль не снимает: понижение — отдельное
осознанное действие, а не следствие правки `.env`.

Зависимость `require_role` проверяет роль на бэкенде. `support` в этом
подпроекте отличается от `user` только тем, что проходит гейт `/api/admin/*`;
разграничение внутри админки появится вместе с её страницами.

Статус `banned` проверяется на каждом входе и при каждом запросе — по значению
из кэша роли и статуса. Интерфейса блокировки здесь нет: он появится в админке
подпроекта 5, а до тех пор статус меняется в БД руками. Проверка написана
сразу, потому что дописывать её к четырём способам входа задним числом — это
ровно тот случай, когда в одном из них её забывают.

## 7. Защита от перебора

Argon2id считается всегда, даже для неизвестного адреса: иначе существование
аккаунта выдаст время ответа.

Лимиты на Valkey скользящим окном, ответ `429` в общем формате ошибок с
`Retry-After`:

| Операция | Лимит |
|---|---|
| Вход паролем | 10/мин по IP, 5/мин по адресу |
| Регистрация | 5/час по IP |
| Сброс пароля, повторное письмо | 3/час по адресу, 10/час по IP |
| Обмен `initData` | 30/мин по IP |
| Код привязки Telegram | 5/час по пользователю |
| Параметры passkey | 20/мин по IP |

## 8. Бот

Добавляется к заглушке подпроекта 0:

- `/start` без параметра — приветствие и кнопка приложения; заодно создаёт
  пользователя по `telegram_id`;
- `/start link_XXX` — привязка по правилам раздела 5;
- `/language` — переключение языка кнопками;
- middleware, подтягивающий пользователя и его язык до вызова хендлера.

## 9. Фронтенд

### `packages/core`

Модуль `auth`: access-токен в памяти, единый перехват `401` с single-flight
обновлением — десять параллельных запросов дают один `refresh`, а не десять.
Хуки `useMe`, `useLogin`, `useLogout`, zod-схемы форм, словари кодов ошибок.
Оба приложения берут это отсюда: одинаковое поведение веба и MiniApp
обеспечивается структурой, а не дисциплиной.

### `apps/web`

Маршруты `/login`, `/register`, `/verify-email`, `/forgot-password`,
`/reset-password`, `/account` с разделами «Профиль» и «Безопасность» (пароль,
passkey, сессии, Telegram).

Гейт клиентский: страница кабинета сначала обращается к `refresh` по cookie,
получает access в память и запрашивает `/me`; без токена — редирект на `/login`.
Серверный гейт в Next.js потребовал бы читать refresh-cookie вне
`/auth/refresh`, а вся модель раздела 3 держится на том, что её видит один
эндпоинт.

### `apps/miniapp`

Автоматический обмен `initData` при открытии, экран профиля, переключение
языка. Ошибка обмена показывает экран с кнопкой повторной попытки, а не пустоту.

### `packages/ui`

Новые компоненты — форма, поле пароля с показом, тумблер, диалог подтверждения,
пустое состояние — добавляются в пакет, а не в приложения. Значения цветов и
отступов берутся из токенов бренд-бука.

### i18n

Источник истины о языке — `users.language`. При первом входе берётся из
`language_code` Telegram или `Accept-Language`, дальше меняется только
пользователем. Язык влияет на интерфейс, письма и сообщения бота.

## 10. Конфигурация

Новые переменные окружения (одновременно в `Settings`, `.env.example` и
`docs/deployment.md`):

| Переменная | Назначение |
|---|---|
| `ADMIN_TELEGRAM_IDS` | Список идентификаторов админов через запятую |
| `ACCESS_TOKEN_TTL_MINUTES`, `REFRESH_TOKEN_TTL_DAYS` | Сроки токенов, значения по умолчанию 15 и 30 |
| `TELEGRAM_OIDC_CLIENT_ID`, `TELEGRAM_OIDC_CLIENT_SECRET` | Из BotFather, Bot Settings → Web Login |
| `EMAIL_SENDER` | `smtp` или `log` |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_STARTTLS` | Отправка писем |

В `compose.yml` под профилем `dev` добавляется Mailpit: локально письмо видно в
его интерфейсе, а Playwright читает ссылку подтверждения из его API. Иначе
сквозные тесты вычитывали бы ссылку из логов контейнера.

`docs/deployment.md` дополняется двумя предупреждениями: переключение бота с
legacy-виджета на OpenID Connect в BotFather необратимо, а redirect URI должен
быть зарегистрирован там до первого входа.

## 11. Тестирование

| Уровень | Что проверяется |
|---|---|
| Домен | Политика пароля, нормализация почты, сроки токенов, `can_unlink`, генерация кодов |
| Сервисы (testcontainers) | Регистрация → письмо → подтверждение → вход; вход до подтверждения; занятый адрес; ротация refresh и обнаружение переиспользования; гонка двух вкладок в окне 30 секунд; отзыв сессий; смена почты; сброс пароля с отзывом сессий; привязка Telegram во всех трёх состояниях; запрет снять последний способ входа; повышение до `admin` |
| OIDC | Подделанная подпись, чужой `aud`, истёкший `exp`, неверный `state`, отсутствующий `code_verifier` — на мокнутом JWKS |
| `initData` | Верный HMAC, испорченный, старше суток |
| Passkey | Регистрация и вход через программный аутентификатор, повтор счётчика подписей |
| Лимиты | Превышение даёт `429` с `Retry-After` |
| `outbox` | Задача ретраится при ошибке отправки, дважды не отправляет, соблюдает задержку |
| Фронтенд (Vitest) | Single-flight обновление токена, редирект без токена, схемы форм |
| E2E (Playwright) | Регистрация → письмо из Mailpit → подтверждение → вход → выход; сброс пароля; `/account` без входа уводит на `/login`; отзыв сессии обрывает доступ |

## 12. Критерии приёмки

1. Регистрация по почте создаёт аккаунт без права входа; вход до подтверждения
   отвечает `email_not_verified`.
2. Письмо приходит в Mailpit, ссылка подтверждает адрес и сразу пускает в
   кабинет.
3. Недоступный SMTP не ломает регистрацию: задача остаётся в `outbox` и
   отправляется после восстановления.
4. Обновление токена работает из двух вкладок одновременно и не разлогинивает;
   повторное использование старого токена позже окна отзывает сессию.
5. MiniApp открывается и входит без единого запроса пароля.
6. Passkey регистрируется и пускает в кабинет без пароля.
7. Вход через Telegram в браузере проходит по OIDC; подделанный ID-токен
   отклоняется.
8. Код привязки склеивает аккаунт из MiniApp с аккаунтом из веба; при непустом
   дубле приходит `link_conflict`, а не молчаливое слияние.
9. Единственный способ входа снять нельзя.
10. Пользователь из `ADMIN_TELEGRAM_IDS` проходит `/api/admin/whoami`, обычный
    получает `403`; факт повышения виден в `audit_log`.
11. Отзыв сессии из списка немедленно обрывает доступ этой сессии.
12. Язык хранится за пользователем: письма и бот отвечают на выбранном.
13. `uv run check` проходит целиком на Windows и на Linux.

## 13. Вне области

Тарифы, подписки, любые вызовы бизнес-методов панели, триал и `trial_grants`,
платежи, реферальные ссылки и начисления, страницы админки, тикеты, рассылки,
двухфакторная аутентификация поверх пароля, вход по одноразовой ссылке
без пароля, удаление аккаунта.
