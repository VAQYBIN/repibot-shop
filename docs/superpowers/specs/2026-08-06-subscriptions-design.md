# Подпроект 2 — Подписки и Remnawave

Дата: 2026-08-06
Статус: утверждён
Контекст: [архитектура платформы](./2026-08-04-platform-architecture-design.md),
[идентичность](./2026-08-05-identity-design.md)

---

## 1. Цель

Дать пользователю подписку, а системе — связь с панелью Remnawave. После этого
подпроекта человек выбирает тариф, активирует триал, получает ссылку
подключения, видит потреблённый трафик и управляет своими устройствами. Админ
заводит тарифы через API и начисляет дни руками.

**Критерий готовности:** на чистом развёртывании админ создаёт тариф из сквадов
живой панели, пользователь с привязанным Telegram активирует триал, получает
рабочую ссылку подписки, подключается клиентом, видит своё устройство в кабинете
и отвязывает его — и `uv run check` проходит целиком.

Денег здесь нет. Начисление дней вынесено в отдельный сервис, у которого сейчас
два вызывающих — активация триала и админское действие. В подпроекте 3 к ним
добавится третий, финализация платежа, и больше ничего менять не придётся.

## 2. Что изменилось в панели: 2.8.0 → 3.2.1

Факты взяты из схемы `docs/remnawave-api/api-1.json` версии 3.2.1, а не из
документации. Изменения ломающие, и они переписывают часть архитектуры.

| Было в 2.8.0 | Стало в 3.2.1 | Следствие |
|---|---|---|
| Пользователь адресуется `uuid` | Пользователь адресуется числовым `id`; поля `uuid` в объекте нет вовсе | `users.remnawave_uuid` заменяется на `remnawave_id` |
| `GET /api/users/by-telegram-id/{id}`, `by-email`, `by-tag`, `by-id` | `POST /api/users/resolve` с телом `{id\|shortUuid\|username}` | Поиск пользователя панели идёт по `username`, который считаем сами |
| — | `POST /api/users/{userId}/actions/extend` | Не используем: дату окончания считаем только мы |
| `GET /api/hwid/devices/{userUuid}` | `GET /api/hwid/devices/{userId}` | Устройства читаются по числовому идентификатору |
| `/api/ip-control/*` | `/api/connections/*` | В области подпроекта не участвует |
| События `user.*` без `user.expiration` | Добавлены `user.expiration`, `user.not_connected`, `user.traffic_reset` | Приёмник вебхуков принимает полный набор и игнорирует незнакомое |

Состав пользователя панели в 3.2.1: `id`, `shortUuid`, `username`, `status`,
`trafficLimitBytes`, `trafficLimitStrategy`, `expireAt`, `telegramId`, `email`,
`description`, `tag`, `hwidDeviceLimit`, `externalSquadUuid`, `subscriptionUrl`,
`activeInternalSquads`, `userTraffic`.

Ограничения на `username`: 3–36 символов, `^[a-zA-Z0-9_-]+$`. На `tag`: до 16
символов, `^[A-Z0-9_]+$`.

Архитектурный документ платформы правится вместе с этой спецификацией: версия
панели и название связующего поля в разделе «Разграничение истины».

## 3. Модель данных

### `users`

`remnawave_uuid` (`uuid`) заменяется на `remnawave_id` (`bigint`, уникальный,
`null`). Поле `remnawave_short_uuid` остаётся: его принимает `resolve`. Данных
в проде нет, миграция переносить ничего не должна.

Добавляется `remnawave_subscription_url` (`varchar`, `null`) — значение из
ответа панели, обновляется на каждом примирении. Собирать ссылку из
`REMNAWAVE_BASE_URL` нельзя: публичный домен страницы подписки настраивается в
панели отдельно, а `revoke` меняет `shortUuid`, и собранная однажды ссылка
начала бы вести в никуда.

### `plans`

| Поле | Тип | Замечание |
|---|---|---|
| `code` | `varchar`, уникальный | Машинное имя, по нему тариф ищется в тестах и сидах |
| `name` | `jsonb` | По локалям: `{"ru": "…", "en": "…"}` |
| `description` | `jsonb`, `null` | То же |
| `duration_days` | `integer` | Больше нуля |
| `price_rub` | `numeric(10,2)` | YooKassa принимает сумму строкой вида `199.00`; дробнее копейки не нужно |
| `price_stars` | `integer` | Своя цена, а не пересчёт из рублей |
| `traffic_limit_bytes` | `bigint` | `0` — безлимит, как в панели |
| `traffic_reset_strategy` | `enum` | `NO_RESET` / `DAY` / `WEEK` / `MONTH` / `MONTH_ROLLING` — значения панели один в один |
| `hwid_device_limit` | `integer` | `0` — без ограничения |
| `internal_squad_uuids` | `uuid[]` | Непустой массив; проверяется по списку сквадов панели при сохранении |
| `is_trial` | `boolean` | Триальных тарифов активным может быть не больше одного |
| `is_active` | `boolean` | Снятый флаг убирает тариф отовсюду, включая триал |
| `is_visible` | `boolean` | Скрытый тариф продаётся по прямой ссылке, но не показан в витрине |
| `sort_order` | `integer` | Порядок в витрине |

Тариф не удаляется физически: на него ссылаются подписки и события, а в
подпроекте 3 сошлются платежи. `DELETE` в админском API снимает `is_active`.

Активный триальный тариф может быть только один: частичный уникальный индекс по
`is_trial` с условием `WHERE is_trial AND is_active`. Правило «один триал на
аккаунт» живёт не здесь, а в `trial_grants`.

### `subscriptions`

Одна строка на пользователя, `user_id` уникальный.

| Поле | Тип | Замечание |
|---|---|---|
| `user_id` | FK на `users`, уникальный | Каскадное удаление вместе с аккаунтом |
| `plan_id` | FK на `plans` | Без каскада: тариф не удаляется |
| `status` | `enum` | `trial` / `active` / `expired` / `disabled` / `pending_provision` |
| `started_at` | `timestamptz` | Момент первой выдачи |
| `expires_at` | `timestamptz` | Наша истина, панель к ней приводится |
| `auto_renew_enabled` | `boolean` | Заполняется в подпроекте 3, заводится сразу |
| `source` | `enum` | `trial` / `purchase` / `gift` / `admin` |

`payment_method_id` не заводится: колонка требует таблицы `payment_methods` из
подпроекта 3 и добавится там одной миграцией.

Статусы означают: `pending_provision` — дни начислены, панель ещё не знает;
`disabled` — доступ снят админом при живой дате; `expired` — дата прошла.

### `subscription_events`

Журнал начислений: `user_id`, `type` (`trial` / `purchase` / `renew` /
`plan_change` / `bonus_days` / `gift` / `expired` / `admin_grant` /
`admin_revoke`),
`days_delta`, `plan_id`, `actor` (`user` / `admin` / `system`), `actor_user_id`
(`null` у системы), `comment`, `created_at`. Ссылка на платёж добавится в
подпроекте 3.

Текущее состояние читается из `subscriptions` одним запросом, а разбор спорного
случая — из журнала. Одно без другого не работает: состояние не помнит, откуда
взялись дни, а журнал не отвечает на вопрос «сколько осталось» без свёртки.

### `trial_grants`

`telegram_id` первичным ключом, `granted_at`, `user_id` (FK с `ON DELETE SET
NULL`). Таблица переживает удаление аккаунта: иначе триал накручивается удалением
и повторной регистрацией.

### `reconciliation_findings`

`id`, `run_id` (`uuid` прогона), `user_id`, `field`, `ours` (`text`), `theirs`
(`text`), `action` (`fixed` / `skipped`), `created_at`. Расхождение почти всегда
означает ручную правку админа в панели, и о ней надо знать. Молчаливое
исправление недопустимо, поэтому запись делается всегда, а не только при отказе.

### `webhook_events`

`source` (`remnawave` / `yookassa`), `event_id`, `event`, `payload` (`jsonb`),
`received_at`, `processed_at`, уникальный индекс по паре `(source, event_id)`.
Панель своего идентификатора события не присылает, поэтому `event_id` собирается
как `<event>:<timestamp>:<идентификатор из data, если он есть>` — этого
достаточно, чтобы повторная доставка не сработала дважды. Идентификатор берётся
из `data.id` для событий пользователя, из `data.user.id` для событий устройств и
опускается там, где его нет.

## 4. Примирение с панелью

Ядро подпроекта — одна идемпотентная функция в `services/provisioning.py`:

```
reconcile_panel_user(session, user_id) -> PanelUser
```

Она читает нашу подписку, находит пользователя панели и приводит панель к нашему
состоянию. Сравниваются `expireAt`, `status`, `trafficLimitBytes`,
`trafficLimitStrategy`, `hwidDeviceLimit`, `activeInternalSquads`. Если всё
сошлось, изменяющего запроса не делается вовсе.

Поиск пользователя: по сохранённому `remnawave_id`, при его отсутствии — по
`username` через `POST /api/users/resolve`. Не нашёлся — создаётся через
`POST /api/users` с `username = rp_<id в base36>`, `tag = REPIBOT`, `telegramId`
и `email` из нашего профиля. Найденный по имени пользователь означает, что мы
теряли `remnawave_id`: он подхватывается, а не дублируется.

`tag = REPIBOT` нужен реконсиляции: по нему видно, каких пользователей панели
ведём мы, а каких админ завёл руками. Чужих не трогаем.

Дату окончания двигаем только мы, поэтому `POST /api/users/{userId}/actions/extend`
не используется: он считает дату на стороне панели и при повторе задачи начислит
дни второй раз. Пишем абсолютное значение через `PATCH /api/users`.

Три вызывающих:

1. **Сервис подписки** — сразу после коммита, с коротким таймаутом
   (`REMNAWAVE_PROVISION_TIMEOUT_SECONDS`, по умолчанию 3 секунды). Успех —
   ответ API несёт ссылку подписки, подписка переходит из `pending_provision` в
   рабочий статус. Неудача глушится: она уже покрыта записью в `outbox`.
2. **Воркер** — задача `provision_subscription` из `outbox`, с ретраями до
   успеха.
3. **Крон-реконсиляция** — по всем подпискам в статусах `trial`, `active` и
   `pending_provision`.

Изменение подписки и запись в `outbox` идут одной транзакцией. Синхронный вызов
делается после коммита, вне транзакции: иначе медленная панель держит блокировки
строк, а её отказ откатывает уже принятое решение о начислении дней.

## 5. Сценарии

### Активация триала

Требует привязанного Telegram — почту накрутить тривиально. Проверка идёт по
`trial_grants` и по `telegram_id`, а не по аккаунту. Активная или истёкшая
подписка любого происхождения закрывает триал: он для новых, а не для
вернувшихся.

В одной транзакции: запись в `trial_grants`, создание `subscriptions` со
статусом `pending_provision` и `source = trial`, событие в
`subscription_events`, задача в `outbox`. Дальше — синхронная попытка
примирения.

Триал выключается снятием `is_active` у триального тарифа. Отдельной переменной
окружения для этого нет: два выключателя одного поведения рано или поздно
расходятся.

### Начисление дней

`grant_days(user_id, plan, days, source, actor)` — единственная функция,
двигающая `expires_at`. Правило сдвига живёт в домене: активная подписка
продлевается от даты окончания, истёкшая — от текущего момента.

### Смена тарифа

При активной подписке остаток пересчитывается в деньги по стоимости дня текущего
тарифа и делится на стоимость дня нового. Возвраты не нужны, оплаченное не
теряется. Поведение выключается настройкой `PLAN_CHANGE_KEEPS_REMAINDER`:
альтернатива — заменить тариф, потеряв остаток.

Смена тарифа меняет и лимиты со сквадами, поэтому всегда заканчивается
примирением.

### Истечение

Крон `expire_subscriptions` раз в час переводит подписки с прошедшей датой в
`expired` и снимает доступ в панели. Дата окончания при этом не двигается:
`expired` — следствие даты, а не отдельное решение.

Уведомлений здесь нет, они появятся в подпроекте 4.

### Устройства

Список читается из `GET /api/hwid/devices/{userId}` и кэшируется в Valkey на
`PANEL_CACHE_TTL_SECONDS` (60 секунд). Отвязка — `POST /api/hwid/devices/delete`
с `hwid` и `userId`, после чего кэш пользователя сбрасывается немедленно: иначе
человек нажимает кнопку и минуту видит удалённое устройство.

Отвязка ограничена по частоте (`DEVICE_UNLINK_LIMIT_PER_DAY`, по умолчанию 10 в
сутки на пользователя, счётчик в Valkey). Ограничение защищает не нас, а панель:
без него скрипт крутит отвязку в цикле и обходит лимит устройств тарифа.

Отвязать можно только своё устройство: принадлежность проверяется по `userId` в
ответе панели, а не по факту, что клиент прислал знакомый `hwid`.

### Трафик

Потребление читается из `userTraffic` в объекте пользователя и из
`GET /api/bandwidth-stats/users/{userId}` для разбивки по дням. Кэш — те же 60
секунд. У себя трафик не дублируется: он меняется постоянно, и наша копия всегда
была бы устаревшей.

### Вебхуки панели

`POST /webhook/remnawave`. Источник подтверждается HMAC-подписью тела в
заголовке; имя заголовка и секрет — из настроек
(`REMNAWAVE_WEBHOOK_HEADER`, `REMNAWAVE_WEBHOOK_SECRET`), потому что задаются на
стороне панели. Подпись сверяется по сырому телу запроса до разбора JSON и
сравнивается за постоянное время.

Событие пишется в `webhook_events` и обрабатывается идемпотентно. Реакция:

| Событие | Что делаем |
|---|---|
| `user.expired`, `user.limited`, `user.disabled`, `user.enabled` | Сверяем со своим состоянием, при расхождении ставим задачу примирения |
| `user.first_connected` | Отмечаем факт подключения — понадобится win-back в подпроекте 4 |
| `user_hwid_devices.added`, `user_hwid_devices.deleted` | Сбрасываем кэш устройств |
| `user.revoked`, `user.modified`, `user.deleted` | Ставим задачу примирения: панель изменили мимо нас |
| остальные | Пишем и игнорируем |

Ни одно событие панели не двигает `expires_at`. Вебхук — повод посмотреть, а не
источник биллинга.

### Реконсиляция

Крон `reconcile_panel` с интервалом `RECONCILE_INTERVAL_HOURS` (по умолчанию 6)
проходит по подпискам в рабочих статусах, вызывает примирение и пишет найденные
расхождения в `reconciliation_findings` с идентификатором прогона.

Прогон идёт от наших подписок, а не от списка пользователей панели. Тег
проверяется перед изменяющим запросом: если у найденного пользователя панели тег
не `REPIBOT`, расхождение записывается с `action = skipped` и панель не
правится. Так админская правка чужой записи не затирается автоматикой.

## 6. API

### Клиентские

```
GET    /api/plans                     витрина: активные и видимые, с локализованными названиями
GET    /api/me/subscription           состояние, тариф, дата окончания, ссылка подключения
POST   /api/me/subscription/trial     активировать триал
GET    /api/me/devices                устройства и лимит тарифа
POST   /api/me/devices/unlink         отвязать своё устройство, `hwid` в теле
GET    /api/me/traffic                потребление и разбивка по дням
```

`GET /api/me/subscription` отвечает и тогда, когда подписки нет: `null` вместо
объекта плюс признак доступности триала. Иначе фронтенду пришлось бы отличать
«нет подписки» от ошибки по коду ответа.

### Админские

```
GET    /api/admin/plans                    все тарифы, включая скрытые и архивные
POST   /api/admin/plans                    создать
PATCH  /api/admin/plans/{id}               править
DELETE /api/admin/plans/{id}               архивировать (is_active = false)
GET    /api/admin/remnawave/squads         внутренние сквады панели для выбора uuid
POST   /api/admin/users/{id}/subscription  начислить дни или сменить тариф
```

Роль `support` к тарифам доступа не имеет — это правило архитектуры, а не
частный случай. Каждое админское действие пишется в `audit_log` с состоянием до
и после.

Интерфейса к этим эндпоинтам в подпроекте 2 нет: он приходит в подпроекте 5 и
садится на готовый контракт.

### Вебхук

```
POST   /webhook/remnawave
```

## 7. Интерфейсы

**Веб.** `/plans` — витрина тарифов. `/account/subscription` — карточка
подписки: состояние, дата окончания, ссылка подключения с копированием и QR,
полоса трафика, список устройств с отвязкой. Кнопка «Попробовать бесплатно»
показывается, пока триал доступен.

**MiniApp.** Те же данные экранами «Подписка» и «Устройства».

Хуки TanStack Query, схемы `zod` и словари — общие, в `packages/core`.
Различается только оболочка: SPA в Telegram и SSR в вебе. Цвета, отступы и
типографика — из бренд-бука через токены `packages/ui`.

**Бот** не трогается: он остаётся тонким, подписка живёт в MiniApp.

Состояние `pending_provision` показывается отдельно — «выдаём доступ, обычно до
минуты», с опросом раз в несколько секунд. Пустой экран без объяснения в этом
месте выглядит как поломка.

## 8. Настройки окружения

Новые переменные. Каждая добавляется одновременно в `Settings`, `.env.example` и
`docs/deployment.md`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `REMNAWAVE_WEBHOOK_SECRET` | пусто | Секрет HMAC. Пусто — вебхуки не принимаются, эндпоинт отвечает 503 |
| `REMNAWAVE_WEBHOOK_HEADER` | `x-remnawave-signature` | Имя заголовка подписи; сверяется с настройкой панели при развёртывании |
| `REMNAWAVE_PROVISION_TIMEOUT_SECONDS` | `3.0` | Таймаут синхронной попытки примирения |
| `PANEL_CACHE_TTL_SECONDS` | `60` | Кэш трафика и устройств |
| `DEVICE_UNLINK_LIMIT_PER_DAY` | `10` | Отвязок устройства в сутки на пользователя |
| `PLAN_CHANGE_KEEPS_REMAINDER` | `true` | Конвертировать остаток при смене тарифа |
| `RECONCILE_INTERVAL_HOURS` | `6` | Интервал крона реконсиляции |

Имя заголовка подписи вынесено в настройку намеренно: в схеме панели его нет —
вебхуки исходящие, — и подтвердить его можно только на живой панели.

## 9. Отказы

Панель недоступна — операция не падает. Подписка остаётся в
`pending_provision`, задача лежит в `outbox`, интерфейс объясняет ожидание. Это
и есть причина, по которой `outbox` появился в подпроекте 0.

Трафик и устройства при недоступной панели отдают `503` с кодом
`panel_unavailable`. Карточка подписки при этом рисуется целиком: недоступен
только её блок. Данные о подписке лежат у нас, и терять весь экран из-за чужого
отказа нечестно.

Коды ошибок этапа. Тексты не локализуются: ответ несёт код, фразу подбирает
фронтенд.

| Код | Когда |
|---|---|
| `panel_unavailable` | Панель не ответила после всех попыток |
| `trial_already_used` | Триал по этому Telegram уже выдавался |
| `trial_requires_telegram` | Telegram не привязан |
| `trial_disabled` | Активного триального тарифа нет |
| `subscription_exists` | Подписка уже есть или была — триал не положен |
| `plan_not_found` | Тарифа нет |
| `plan_code_taken` | Тариф с таким кодом уже заведён |
| `plan_inactive` | Тариф архивирован или скрыт |
| `plan_squads_unknown` | В тарифе сквад, которого нет в панели |
| `subscription_missing` | Действие требует подписки, а её нет |
| `device_not_found` | Устройства нет или оно чужое |
| `too_many_requests` | Превышен лимит отвязок |

## 10. Тестирование

| Уровень | Что покрывается |
|---|---|
| Домен, pytest без БД | Границы сдвига даты, конвертация остатка при смене тарифа, правила триала, генерация `username` |
| Сервисы, pytest + testcontainers | Активация триала, начисление, смена тарифа, истечение, отвязка устройства — с заглушкой панели |
| Примирение | Повторный вызов на сошедшихся данных не делает изменяющих запросов; потерянный `remnawave_id` подхватывается по имени |
| Вебхуки | Битая подпись, повторная доставка, незнакомое событие, гонка вебхука и крона |
| Фронтенд, Vitest | Хуки подписки и устройств, форматирование байт и дат, состояние `pending_provision` |
| Сквозной, Playwright | Регистрация, привязка Telegram, активация триала, появление ссылки подписки, отвязка устройства |

Заглушка панели (`testing/remnawave.py`) держит пользователей в памяти и
повторяет поведение 3.2.1: числовой `id`, `resolve` по трём ключам, отказ на
неизвестном пользователе. Она проверяет наш код, но не панель.

**Проверка на живой панели остаётся ручной** и входит в план отдельным пунктом:
схема описывает форму ответов, а не поведение. Ручной проверкой подтверждаются
как минимум имя заголовка подписи вебхука, формат `subscriptionUrl` и то, что
созданный нами пользователь действительно подключается клиентом.

## 11. Вне области

- Оплата любым способом — подпроект 3.
- Уведомления об истечении и приближении конца срока — подпроект 4.
- Интерфейс админки поверх админских эндпоинтов — подпроект 5.
- Управление нодами и их состоянием — подпроект 5.
- Подарочные ваучеры и промокоды — подпроект 3, хотя дни им начислит тот же
  `grant_days`.
- Автопродление: колонка заводится, логика — подпроект 3.
