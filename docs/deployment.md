# Развёртывание

## Что понадобится

- Сервер с Docker и Docker Compose.
- Домен с сертификатом TLS.
- Панель Remnawave 2.8.1 — на этом же сервере или на другом.
- Бот, созданный в @BotFather.

## 1. Панель Remnawave

Создайте в панели API-токен (раздел API Tokens) и запишите его в `REMNAWAVE_TOKEN`.

Адрес панели зависит от размещения:

- Панель на другом сервере: `REMNAWAVE_BASE_URL=https://panel.example.org`
- Панель рядом: `REMNAWAVE_BASE_URL=http://remnawave:3000`, запуск с оверлеем
  `docker compose -f compose.yml -f compose.local-panel.yml up -d`. Имя внешней сети
  в `compose.local-panel.yml` должно совпадать с сетью вашей панели.

## 2. Бот и вход через Telegram

В @BotFather получите токен бота — это `BOT_TOKEN`.

Вход через Telegram на сайте работает по OpenID Connect. Настройки задаются
**в мини-приложении @BotFather**, через обычный чат этот раздел недоступен:

1. Откройте мини-приложение BotFather, выберите бота.
2. Bot Settings → Web Login.
3. Скопируйте **Client ID** и **Client Secret** — это `TELEGRAM_OIDC_CLIENT_ID`
   и `TELEGRAM_OIDC_CLIENT_SECRET`.
4. В **Redirect URIs** добавьте `https://ваш-домен/api/auth/telegram/callback`.
5. В **Trusted Origins** добавьте `https://ваш-домен/`.

Адрес возврата собирается из `PUBLIC_WEB_URL` и всегда лежит под `/api` — этот
префикс отдаёт Nginx бэкенду, страницы сайта туда не попадают. Адреса должны
совпадать точно, включая `/api`, протокол и завершающий слеш. Расхождение
проявляется отказом на этапе обмена кода на токен.

Кнопка «Войти через Telegram» появляется на странице входа, как только задан
`TELEGRAM_OIDC_CLIENT_ID`. Без `TELEGRAM_OIDC_CLIENT_SECRET` она видна, но вход
обрывается на обмене кода: заполнять нужно обе переменные сразу.

> **Переключение бота на OpenID Connect необратимо.** BotFather не возвращает
> бота к прежнему виджету Telegram Login. Если на этом же боте работает другой
> сайт со старой кнопкой входа, он перестанет пускать людей. Проверять
> переключение лучше на отдельном тестовом боте.

> **Redirect URI регистрируется до первого входа.** Незарегистрированный адрес
> Telegram отвергает на самом первом шаге, и это выглядит как поломка сайта, а
> не как незаполненная настройка. Меняя домен, добавьте новый адрес в BotFather
> раньше, чем переключите DNS.

> **Cookie `repibot_oidc` вырезать нельзя.** Начатый вход привязывается к
> браузеру короткоживущей httpOnly-cookie с путём `/api/auth/telegram`: без неё
> подсунутая жертве ссылка возврата с чужим кодом молча усадила бы её в чужой
> аккаунт. Возврат сравнивает cookie с записью в Valkey, и если промежуточный
> прокси или CDN режет заголовки `Cookie` и `Set-Cookie` на `/api`, вход
> заканчивается ошибкой `token_invalid` — при работающих в остальном запросах.
> Живёт cookie десять минут и гасится сразу после попытки.

## 3. Переменные окружения

```bash
cp .env.example .env
```

Обязательно заполнить: `BOT_TOKEN`, `BOT_WEBHOOK_SECRET`, `BOT_WEBHOOK_BASE_URL`,
`REMNAWAVE_BASE_URL`, `REMNAWAVE_TOKEN`, `JWT_SECRET`, `ENCRYPTION_KEY`,
`POSTGRES_PASSWORD`, `PUBLIC_WEB_URL`, `PUBLIC_APP_URL`.

`TELEGRAM_OIDC_CLIENT_ID` и `TELEGRAM_OIDC_CLIENT_SECRET` необязательны: без них
работают все остальные способы входа, а кнопки «Войти через Telegram» на сайте
просто нет.

`POSTGRES_PASSWORD` встречается дважды: отдельной переменной и внутри
`DATABASE_URL`. Значения должны совпадать, иначе миграции не подключатся к базе.

Внутри `DATABASE_URL` пароль — часть адреса, и служебные символы в нём нужно
кодировать процентами: `@` → `%40`, `:` → `%3A`, `/` → `%2F`, `?` → `%3F`,
`#` → `%23`, `%` → `%25`. Незакодированный `@` обрывает адрес на своём месте,
и подключение уходит на несуществующий хост. Отдельная переменная
`POSTGRES_PASSWORD` кодирования не требует — там пароль передаётся как есть,
поэтому при экранировании они перестают совпадать буквально. Надёжнее взять
пароль без служебных символов:

```bash
openssl rand -hex 16
```

Секреты генерируются так:

```bash
openssl rand -hex 32
```

`BOT_WEBHOOK_SECRET` Telegram присылает в заголовке `X-Telegram-Bot-Api-Secret-Token`
на каждом запросе; это единственное, что подтверждает подлинность вебхука. Меняя
значение, перезапустите бота — он переустанавливает вебхук на старте.

В самом адресе секрета нет. Вебхуки приходят на постоянные пути вида
`/webhook/<источник>`: сейчас это `/webhook/telegram`, позже добавится
`/webhook/yookassa`. URL целиком попадает в журнал доступа Nginx, в панель
туннеля при локальной отладке и в любой промежуточный прокси — секрету там
не место.

## 4. Почта, сессии и админы

Подтверждение почты и сброс пароля отправляются письмом. **Без работающей
отправки регистрация бесполезна:** без подтверждённого адреса войти нельзя.
Способ отправки задаёт `EMAIL_SENDER`:

- `log` (по умолчанию) — письмо не уходит никуда, кроме журнала контейнера `api`
  или `worker`. Регистрация и вход работают, но ссылку подтверждения нужно
  искать в логах (`docker compose logs -f worker` при `LOG_LEVEL=DEBUG`) —
  почтового сервера в развёртывании нет.
- `smtp` — реальная отправка. Заполните `SMTP_HOST`, `SMTP_PORT`,
  `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_STARTTLS` под ваш
  почтовый сервис. Пустые `SMTP_USERNAME` и `SMTP_PASSWORD` означают отправку
  без аутентификации — так работает локальный релей.

Недоступный SMTP регистрацию не ломает: письмо лежит в таблице `outbox`, и
`worker` повторяет попытку с растущей задержкой, пока не отправит. Застрявшие
задачи видно там же — в колонке `last_error`.

Локально письма удобно смотреть в Mailpit: `docker compose --profile dev up -d
mailpit`, затем `EMAIL_SENDER=smtp`, `SMTP_HOST=mailpit`, `SMTP_PORT=1025` и
интерфейс на `http://localhost:8025`. Профиль `dev` означает, что в обычном
развёртывании этот контейнер не поднимается.

Сроки жизни токенов задают `ACCESS_TOKEN_TTL_MINUTES` (по умолчанию 15) и
`REFRESH_TOKEN_TTL_DAYS` (30). Access-токен живёт в памяти вкладки, refresh —
в httpOnly-cookie. Увеличивать первый не стоит: заблокированный пользователь
теряет доступ не позже, чем истечёт его access-токен.

Первый админ назначается через `ADMIN_TELEGRAM_IDS` — список идентификаторов
Telegram через запятую. Свой ID можно узнать у @userinfobot. Роль поднимается не
сразу при добавлении в список, а в момент входа: назначенному админу нужно один
раз войти через Telegram, чтобы роль применилась и факт был записан в
`audit_log`. Удаление идентификатора из списка роль не снимает — понижение
делается осознанно, а не правкой `.env`.

## 5. Ключи доступа (passkey)

Отдельных настроек у них нет: идентификатор проверяющей стороны (RP ID)
выводится из `PUBLIC_WEB_URL` — это имя домена без схемы и порта.

> **Смена домена делает все зарегистрированные ключи бесполезными.** Ключ
> привязан к домену на стороне устройства, и перенести его нельзя ничем: после
> переезда людям придётся заводить ключи заново. Тем, у кого passkey был
> единственным способом входа, останется только восстановление по почте.

Ключи работают только по HTTPS. Исключение — `localhost`, который браузеры
считают безопасным контекстом; на локальном адресе без TLS они тоже заведутся.

## 6. TLS

Конфигурация Nginx в репозитории слушает только 80 порт: сертификаты выпускаются
на конкретный домен, и держать в открытом проекте чужой домен бессмысленно.

Варианты:

- Внешний обратный прокси (Caddy, Traefik) перед контейнером `nginx`.
- Certbot и монтирование сертификатов в контейнер `nginx` с добавлением
  секции `listen 443 ssl` в `docker/nginx.conf`.

Telegram принимает вебхуки только по HTTPS — без TLS бот работать не будет.

Раз TLS терминирует внешний прокси, до Nginx запрос доходит по http, и в конфиге
стоит `absolute_redirect off`: иначе редирект на каталог (`/app` → `/app/`)
собирался бы как `http://домен/app/` и уводил бы пользователя с https.

Заголовки безопасности вынесены в `docker/security-headers.conf` и подключаются
через `include` в каждой локации, которая объявляет собственные `add_header`.
Так задумано: `add_header` внутри `location` заменяет унаследованный от `server`
набор целиком, поэтому добавление одного заголовка без `include` молча выключает
остальные, включая HSTS.

## 7. Запуск

```bash
docker compose build
docker compose up -d
docker compose ps
curl https://ваш-домен/health
```

Ожидаемо: все сервисы в состоянии `running`, кроме `migrate` — он одноразовый
и завершается кодом 0. Проверка живости возвращает
`{"status":"ok","database":true,"valkey":true}`.

## 8. Обновление

```bash
git pull
docker compose build
docker compose up -d
```

Миграции применяет сервис `migrate` до старта остальных — вручную ничего запускать
не нужно.

## Диагностика

| Симптом | Причина |
|---|---|
| `migrate` завершается с ошибкой | Недоступен Postgres или неверный `DATABASE_URL` |
| `/health` отдаёт `database: false` | Контейнер базы не поднялся, смотрите `docker compose logs postgres` |
| Бот не отвечает | Проверьте `BOT_WEBHOOK_BASE_URL`, TLS и `docker compose logs bot` |
| Бот пишет `Unauthorized: invalid token specified` | Неверный `BOT_TOKEN`, возьмите его заново у @BotFather |
| Задачи не выполняются | Работать должны оба сервиса: `worker` и `scheduler` |
| Панель не отвечает | Проверьте `REMNAWAVE_TOKEN` и сетевую доступность из контейнера `api` |
| Вход через Telegram возвращает на `/login?error=token_invalid` | Redirect URI в BotFather не совпадает с `https://ваш-домен/api/auth/telegram/callback` либо прокси режет cookie `repibot_oidc` |
| Кнопки «Войти через Telegram» нет | Пуст `TELEGRAM_OIDC_CLIENT_ID` |
| Ключи доступа перестали пускать | Сменился домен: RP ID выводится из `PUBLIC_WEB_URL`, ключи нужно завести заново |
