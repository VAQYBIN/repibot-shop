# Развёртывание

## Что понадобится

- Сервер с Docker и Docker Compose.
- Домен с сертификатом TLS.
- Панель Remnawave 3.2.1 — на этом же сервере или на другом.
- Бот, созданный в @BotFather.

## 1. Панель Remnawave

Создайте в панели API-токен (раздел API Tokens) и запишите его в `REMNAWAVE_TOKEN`.

Адрес панели зависит от размещения:

- Панель на другом сервере: `REMNAWAVE_BASE_URL=https://panel.example.org`
- Панель рядом: `REMNAWAVE_BASE_URL=http://remnawave:3000`, запуск с оверлеем
  `docker compose -f compose.yml -f compose.local-panel.yml up -d`. Имя внешней сети
  в `compose.local-panel.yml` должно совпадать с сетью вашей панели.

### Вебхуки Remnawave

В настройках вебхуков панели создайте исходящий вебхук с адресом
`https://ваш-домен/webhook/remnawave`. Сгенерируйте там отдельный длинный
случайный секрет и перенесите его без изменений в
`REMNAWAVE_WEBHOOK_SECRET`. Имя заголовка, в котором панель отправляет подпись,
запишите в `REMNAWAVE_WEBHOOK_HEADER`; приложение по умолчанию ожидает
`x-remnawave-signature`.

Подпись — шестнадцатеричный HMAC-SHA256 сырого тела запроса. Префикс
`sha256=` допустим, но не обязателен. Имя заголовка не описано в OpenAPI-схеме
Remnawave 3.2.1, поэтому его нужно сверить с интерфейсом именно вашей
установки, а при несовпадении изменить `REMNAWAVE_WEBHOOK_HEADER`.

Включите события:

- `user.modified`, `user.deleted`, `user.revoked`, `user.disabled`,
  `user.enabled`, `user.limited`, `user.expired` — они ставят примирение с
  нашим состоянием в очередь;
- `user_hwid_devices.added`, `user_hwid_devices.deleted` — они сразу сбрасывают
  минутный кэш списка устройств.

Остальные события пользователя можно отправлять на тот же адрес: они будут
идемпотентно записаны в `webhook_events`, но сами по себе не меняют срок
подписки. Источник истины для срока — база магазина, не панель.

> **Пустой `REMNAWAVE_WEBHOOK_SECRET` означает «вебхуки не настроены».** Такие
> запросы отвергаются, а не принимаются на веру: неподписанное событие
> «подписка продлена» пришло бы от кого угодно. Пока секрет пуст, состояние
> подтягивает сверка по расписанию — с задержкой, но без дыры.

## 2. Бот и вход через Telegram

В @BotFather получите токен бота — это `BOT_TOKEN`.

Вход через Telegram на сайте работает по OpenID Connect. Настройки задаются
**в мини-приложении @BotFather**, через обычный чат этот раздел недоступен:

1. Откройте мини-приложение BotFather, выберите бота.
2. Bot Settings → Web Login.
3. Скопируйте **Client ID** и **Client Secret** — это `TELEGRAM_OIDC_CLIENT_ID`
   и `TELEGRAM_OIDC_CLIENT_SECRET`.
4. В **Redirect URIs** добавьте `https://ваш-домен/api/auth/telegram/callback`.
5. В **Trusted Origins** добавьте `https://ваш-домен/`.

Адрес возврата собирается из `PUBLIC_WEB_URL` и всегда лежит под `/api` — этот
префикс отдаёт Nginx бэкенду, страницы сайта туда не попадают. Адреса должны
совпадать точно, включая `/api`, протокол и завершающий слеш. Расхождение
проявляется отказом на этапе обмена кода на токен.

Кнопка «Войти через Telegram» появляется на странице входа, как только задан
`TELEGRAM_OIDC_CLIENT_ID`. Без `TELEGRAM_OIDC_CLIENT_SECRET` она видна, но вход
обрывается на обмене кода: заполнять нужно обе переменные сразу.

> **Переключение бота на OpenID Connect необратимо.** BotFather не возвращает
> бота к прежнему виджету Telegram Login. Если на этом же боте работает другой
> сайт со старой кнопкой входа, он перестанет пускать людей. Проверять
> переключение лучше на отдельном тестовом боте.

> **Redirect URI регистрируется до первого входа.** Незарегистрированный адрес
> Telegram отвергает на самом первом шаге, и это выглядит как поломка сайта, а
> не как незаполненная настройка. Меняя домен, добавьте новый адрес в BotFather
> раньше, чем переключите DNS.

> **Cookie `repibot_oidc` вырезать нельзя.** Начатый вход привязывается к
> браузеру короткоживущей httpOnly-cookie с путём `/api/auth/telegram`: без неё
> подсунутая жертве ссылка возврата с чужим кодом молча усадила бы её в чужой
> аккаунт. Возврат сравнивает cookie с записью в Valkey, и если промежуточный
> прокси или CDN режет заголовки `Cookie` и `Set-Cookie` на `/api`, вход
> заканчивается ошибкой `token_invalid` — при работающих в остальном запросах.
> Живёт cookie десять минут и гасится сразу после попытки.

## 3. Переменные окружения

```bash
cp .env.example .env
```

Обязательно заполнить: `BOT_TOKEN`, `BOT_WEBHOOK_SECRET`, `BOT_WEBHOOK_BASE_URL`,
`REMNAWAVE_BASE_URL`, `REMNAWAVE_TOKEN`, `JWT_SECRET`,
`ADMIN_ASSERTION_SECRET`, `ENCRYPTION_KEY`, `POSTGRES_PASSWORD`,
`PUBLIC_WEB_URL`, `PUBLIC_APP_URL`.

`TELEGRAM_OIDC_CLIENT_ID` и `TELEGRAM_OIDC_CLIENT_SECRET` необязательны: без них
работают все остальные способы входа, а кнопки «Войти через Telegram» на сайте
просто нет.

`POSTGRES_PASSWORD` встречается дважды: отдельной переменной и внутри
`DATABASE_URL`. Значения должны совпадать, иначе миграции не подключатся к базе.

Внутри `DATABASE_URL` пароль — часть адреса, и служебные символы в нём нужно
кодировать процентами: `@` → `%40`, `:` → `%3A`, `/` → `%2F`, `?` → `%3F`,
`#` → `%23`, `%` → `%25`. Незакодированный `@` обрывает адрес на своём месте,
и подключение уходит на несуществующий хост. Отдельная переменная
`POSTGRES_PASSWORD` кодирования не требует — там пароль передаётся как есть,
поэтому при экранировании они перестают совпадать буквально. Надёжнее взять
пароль без служебных символов:

```bash
openssl rand -hex 16
```

Секреты генерируются так:

```bash
openssl rand -hex 32
```

`BOT_WEBHOOK_SECRET` Telegram присылает в заголовке `X-Telegram-Bot-Api-Secret-Token`
на каждом запросе; это единственное, что подтверждает подлинность вебхука. Меняя
значение, перезапустите бота — он переустанавливает вебхук на старте.

В самом адресе секрета нет. Вебхуки приходят на постоянные пути вида
`/webhook/<источник>`: сейчас это `/webhook/telegram`, позже добавится
`/webhook/yookassa`. URL целиком попадает в журнал доступа Nginx, в панель
туннеля при локальной отладке и в любой промежуточный прокси — секрету там
не место.

Настройки панели, подписок и очереди уведомлений заполнены разумно по
умолчанию — трогать их нужно только при видимой причине:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `REMNAWAVE_WEBHOOK_SECRET` | пусто | Секрет подписи вебхуков панели. Пустой — вебхуки не принимаются вовсе |
| `REMNAWAVE_WEBHOOK_HEADER` | `x-remnawave-signature` | Заголовок, в котором панель присылает подпись |
| `REMNAWAVE_PROVISION_TIMEOUT_SECONDS` | `3.0` | Ожидание панели при выдаче доступа в запросе пользователя. Короче общего `REMNAWAVE_TIMEOUT_SECONDS`: не дождавшись, доступ добьёт очередь |
| `PANEL_CACHE_TTL_SECONDS` | `60` | Срок жизни кэша справочных данных панели: списков сквадов и лимитов |
| `DEVICE_UNLINK_LIMIT_PER_DAY` | `10` | Сколько устройств пользователь отвязывает за сутки |
| `PLAN_CHANGE_KEEPS_REMAINDER` | `true` | При смене тарифа остаток переезжает в новый днями по стоимости дня. `false` — сгорает |
| `RECONCILE_INTERVAL_HOURS` | `6` | Как часто сверять подписки с панелью |
| `OUTBOX_BATCH_SIZE` | `100` | Сколько сообщений очереди уведомлений разбирается за одну пачку. Допустимо от 1 до 1000 |
| `OUTBOX_CONCURRENCY` | `10` | Сколько отправок внутри пачки идут одновременно. Допустимо от 1 до 50 |

Увеличивать `REMNAWAVE_PROVISION_TIMEOUT_SECONDS` в надежде на надёжность не
нужно: подписка уже записана у нас, а панель догоняется повтором из очереди.
Длинный таймаут лишь заставляет человека ждать ответа дольше.

`OUTBOX_BATCH_SIZE` и `OUTBOX_CONCURRENCY` поднимают тогда, когда очередь
перестаёт разбираться за минуту: задача идёт раз в минуту, и остаток пачки
ждёт следующего прогона. Признак — растущее число неразобранных сообщений
(см. «Диагностика»). Параллельность выше десяти упирается уже не в нас, а в
ограничения Telegram и почтового сервиса.

## 4. Почта, сессии и админы

Подтверждение почты и сброс пароля отправляются письмом. **Без работающей
отправки регистрация бесполезна:** без подтверждённого адреса войти нельзя.
Способ отправки задаёт `EMAIL_SENDER`:

- `log` (по умолчанию) — письмо не уходит никуда, кроме журнала контейнера `api`
  или `worker`. Регистрация и вход работают, но ссылку подтверждения нужно
  искать в логах (`docker compose logs -f worker` при `LOG_LEVEL=DEBUG`) —
  почтового сервера в развёртывании нет.
- `smtp` — реальная отправка. Заполните `SMTP_HOST`, `SMTP_PORT`,
  `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_STARTTLS` под ваш
  почтовый сервис. Пустые `SMTP_USERNAME` и `SMTP_PASSWORD` означают отправку
  без аутентификации — так работает локальный релей.

Недоступный SMTP регистрацию не ломает: письмо лежит в таблице `outbox`, и
`worker` повторяет попытку с растущей задержкой, пока не отправит. Застрявшие
задачи видно там же — в колонке `last_error`.

Локально письма удобно смотреть в Mailpit: `docker compose --profile dev up -d
mailpit`, затем `EMAIL_SENDER=smtp`, `SMTP_HOST=mailpit`, `SMTP_PORT=1025` и
интерфейс на `http://localhost:8025`. Профиль `dev` означает, что в обычном
развёртывании этот контейнер не поднимается.

Сроки жизни токенов задают `ACCESS_TOKEN_TTL_MINUTES` (по умолчанию 15) и
`REFRESH_TOKEN_TTL_DAYS` (30). Access-токен живёт в памяти вкладки, refresh —
в httpOnly-cookie. Увеличивать первый не стоит: заблокированный пользователь
теряет доступ не позже, чем истечёт его access-токен.

`ADMIN_ASSERTION_SECRET` — отдельный HMAC-SHA256-ключ не короче 32 символов;
не переиспользуйте для него `JWT_SECRET`. Compose передаёт его поимённо только
в API и server-side Next, а не в клиентский JavaScript. После browser login или
refresh API ставит для администратора короткую HttpOnly-cookie
`repibot_admin_assertion` с `Path=/admin`; по умолчанию она живёт пять минут,
а `ADMIN_ASSERTION_TTL_SECONDS` допускает только 60–900 секунд. При logout,
неудачном refresh или следующем refresh после понижения роли cookie гасится.

Next проверяет подпись и срок только до рендера `/admin/payments`: отсутствующая,
подменённая или истёкшая cookie ведёт на `/login` без разметки платёжной
админки. Это не разрешение на API: `/api/admin/*` продолжает требовать обычный
access-токен и backend `require_role(admin)`. Поэтому смена роли действует на
мутации немедленно, а на отображение — при следующем refresh либо не дольше
TTL assertion. Убедитесь, что прокси/CDN не срезает `Cookie` на `/admin` и
`Set-Cookie` на `/api/auth/*`.

Первый админ назначается через `ADMIN_TELEGRAM_IDS` — список идентификаторов
Telegram через запятую. Свой ID можно узнать у @userinfobot. Роль поднимается не
сразу при добавлении в список, а в момент входа: назначенному админу нужно один
раз войти через Telegram, чтобы роль применилась и факт был записан в
`audit_log`. Удаление идентификатора из списка роль не снимает — понижение
делается осознанно, а не правкой `.env`.

## 5. Ключи доступа (passkey)

Отдельных настроек у них нет: идентификатор проверяющей стороны (RP ID)
выводится из `PUBLIC_WEB_URL` — это имя домена без схемы и порта.

> **Смена домена делает все зарегистрированные ключи бесполезными.** Ключ
> привязан к домену на стороне устройства, и перенести его нельзя ничем: после
> переезда людям придётся заводить ключи заново. Тем, у кого passkey был
> единственным способом входа, останется только восстановление по почте.

Ключи работают только по HTTPS. Исключение — `localhost`, который браузеры
считают безопасным контекстом; на локальном адресе без TLS они тоже заведутся.

## 6. TLS

Конфигурация Nginx в репозитории слушает только 80 порт: сертификаты выпускаются
на конкретный домен, и держать в открытом проекте чужой домен бессмысленно.

Варианты:

- Внешний обратный прокси (Caddy, Traefik) перед контейнером `nginx`.
- Certbot и монтирование сертификатов в контейнер `nginx` с добавлением
  секции `listen 443 ssl` в `docker/nginx.conf`.

Telegram принимает вебхуки только по HTTPS — без TLS бот работать не будет.

Раз TLS терминирует внешний прокси, до Nginx запрос доходит по http, и в конфиге
стоит `absolute_redirect off`: иначе редирект на каталог (`/app` → `/app/`)
собирался бы как `http://домен/app/` и уводил бы пользователя с https.

Заголовки безопасности вынесены в `docker/security-headers.conf` и подключаются
через `include` в каждой локации, которая объявляет собственные `add_header`.
Так задумано: `add_header` внутри `location` заменяет унаследованный от `server`
набор целиком, поэтому добавление одного заголовка без `include` молча выключает
остальные, включая HSTS.

## 7. Запуск

```bash
docker compose build
docker compose up -d
docker compose ps
curl https://ваш-домен/health
```

Ожидаемо: все сервисы в состоянии `running`, кроме `migrate` — он одноразовый
и завершается кодом 0. Проверка живости возвращает
`{"status":"ok","database":true,"valkey":true}`.

## 8. Платежи, возвраты и автопродление

Заполните обе переменные из кабинета YooKassa: `YOOKASSA_SHOP_ID` и
`YOOKASSA_SECRET_KEY`. Пустая пара отключает оплату картой, заполненная
наполовину не даёт процессу стартовать. В production оставляйте
`YOOKASSA_API_BASE_URL=https://api.yookassa.ru/v3`: HTTP разрешён только для
встроенной local E2E-заглушки и production-конфигурация его отвергает.

В YooKassa укажите callback `https://ваш-домен/webhook/yookassa`. Приложение
берёт из него лишь `object.id`, само читает платёж у YooKassa и сверяет id,
сумму и валюту. Секрет не помещается в URL; поля webhook не являются
доказательством оплаты.

Сохранить карту магазин не просит: запрос на оплату не содержит
`save_payment_method`, поэтому галочку «запомнить карту» показывает сама форма
YooKassa и решение принимает плательщик. Привязка засчитывается только по полю
`payment_method.saved` в прочитанном у провайдера ответе — ни наш запрос, ни
поля webhook доказательством не являются. Успешная оплата с отмеченной галочкой
сохраняет карту и заодно включает автопродление: на повторные списания
пользователь уже согласился, отдельно подтверждать нечего. Снятая галочка не
трогает ни прежнюю карту, ни настройку — она означает «эту карту не
запоминать», а не «отвязать прежнюю». Действующая карта у пользователя одна:
новая заменяет прежнюю.

Отвязка карты в кабинете немедленно выключает автопродление — списывать станет
нечем. На уже выданный доступ и историю заказов отвязка не влияет.

`YOOKASSA_ZERO_AMOUNT_BINDING` (по умолчанию `false`) открывает привязку карты
без списания: отдельный ресурс YooKassa `POST /v3/payment_methods` с типом
`bank_card`. В демо-магазине он доступен сразу, а в боевом его подключает
менеджер YooKassa, поэтому раньше этого включать настройку бессмысленно —
запросы будут отклоняться. Пока она выключена, кнопки «привязать другую карту»
в интерфейсе просто нет.

Включив её, добавьте в тот же callback событие `payment_method.active` — им
YooKassa сообщает об успешной привязке. Событие только указывает, какой ресурс
перечитать: итог, как и у оплаты, берётся из ответа провайдера, а неудачная
привязка возвращается там же как `status=inactive` и `saved=false`. Без этого
события привязка тоже дойдёт: экран карты дочитывает её, когда человек
возвращается с формы, а незакрытые добирает сверка каждые пять минут.

Автопродление использует сохранённый способ оплаты. Попытки задаёт
`AUTO_RENEW_OFFSETS_HOURS` — JSON-массив часов относительно срока подписки, по
умолчанию `[-24, -18, -6]`: за 24 часа до срока, затем через 6 и 12 часов после
предыдущей попытки. Запись через запятую процесс не примет. Переменная
`AUTO_RENEW_DISABLE_AFTER_FINAL_FAILURE=true` выключает выбор после последней
ошибки. Реферальные правила задаются `REFERRAL_REWARD_PERCENT` и
`REFERRAL_REWARD_MODE` (`first` или `every`); ограничения и срок промокодов
сервер проверяет при создании заказа. Gift-ваучер появляется после
подтверждённой оплаты и погашается только раз.

Для Telegram Stars нужен работающий бот, которому разрешено выставлять invoice;
перед релизом выполните одну Stars-оплату только на выделенном тестовом аккаунте.
Проверьте также sandbox YooKassa: success, cancel и возврат. Отдельно пройдите
обе ветки сохранения карты — оплату с отмеченной галочкой и без неё, — а затем
отвяжите карту в кабинете и убедитесь, что автопродление после этого
выключено. Не используйте обычные клиентские платежи или неизвестные реквизиты
для ручных проверок.

Возврат выполняется у провайдера первым. Затем админ в `/admin/payments`
вносит номер заказа, номер возврата и причину: отметка не меняет срок
подписки. Если нужна локальная коррекция, её готовят и подтверждают отдельно;
действие и ключ идемпотентности остаются в audit log. Перед выпуском проверьте
оба канала уведомлений без дублей при повторе, истёкший промокод, gift once,
выбранный referral-режим и все попытки auto-renew на выделенных тестовых данных.

## 9. Первые тарифы

Интерфейса управления тарифами пока нет — он появится вместе с админкой.
Тарифы заводятся через API, и для этого нужен вошедший пользователь с ролью
`admin`: роль поднимается по `ADMIN_TELEGRAM_IDS` при входе через Telegram
(см. раздел 4).

Сначала посмотрите, какие внутренние сквады есть в вашей панели — из них и
собирается тариф:

```bash
curl -H "Authorization: Bearer $ACCESS_TOKEN" https://ваш-домен/api/admin/remnawave/squads
```

Затем создайте тариф, подставив uuid нужных сквадов:

```bash
curl -X POST https://ваш-домен/api/admin/plans \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "code": "month",
    "name": {"ru": "Месяц", "en": "Month"},
    "description": null,
    "duration_days": 30,
    "price_rub": "299.00",
    "price_stars": 199,
    "traffic_limit_bytes": 0,
    "traffic_reset_strategy": "NO_RESET",
    "hwid_device_limit": 3,
    "internal_squad_uuids": ["uuid-сквада-из-ответа-выше"],
    "is_trial": false,
    "is_visible": true,
    "sort_order": 0
  }'
```

`traffic_limit_bytes: 0` означает безлимит, `hwid_device_limit: 0` — без
ограничения на устройства. Цена передаётся строкой: так её принимает и
платёжный провайдер, и двоичная дробь не искажает сумму.

Триальный тариф — такая же запись с `"is_trial": true` и нулевыми ценами.
Активным он может быть только один; чтобы выключить триал целиком, снимите с
него `is_active` запросом `DELETE /api/admin/plans/{id}` — тариф архивируется,
а не удаляется, и история начислений остаётся читаемой.

Тариф со сквадом, которого нет в панели, создать нельзя: такой тариф
продавался бы и не давал доступа.

## 10. Поддержка, напоминания и рассылки

### Супергруппа поддержки

Обращения пользователей персонал ведёт в супергруппе Telegram: каждое
обращение — отдельная тема, ответ в теме уходит человеку письмом или
сообщением бота. Настраивается один раз:

1. Создайте супергруппу. Обычная группа не подойдёт: темы включаются только у
   супергрупп. Если пункта нет, повысьте группу до супергруппы в её настройках.
2. Включите темы: Управление группой → Темы (Topics).
3. Добавьте бота в группу и сделайте администратором. Обязательное право —
   **управление темами**; без него `createForumTopic` отвечает отказом, и
   обращения молча копятся в очереди, а человек ждёт ответа, которого никто не
   увидит.
4. Возьмите идентификатор чата. Он отрицательный и начинается с `-100`:
   перешлите любое сообщение из группы в @userinfobot или откройте группу в
   Telegram Web — номер виден в адресе.
5. Положите его в `SUPPORT_CHAT_ID` и перезапустите `api`, `bot` и `worker`.

Пустой `SUPPORT_CHAT_ID` выключает поддержку целиком. Это рабочая
конфигурация: стенд без супергруппы поднимается и работает, просто кнопки
«Написать в поддержку» на нём нет, а API отвечает отказом `support_unavailable`.

### Переменные

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SUPPORT_CHAT_ID` | пусто | Супергруппа с темами, где персонал ведёт обращения. Пусто — поддержка выключена |
| `TICKET_MAX_OPEN` | `3` | Сколько незакрытых обращений заводит один человек. Допустимо от 1 до 20 |
| `EXPIRY_REMINDER_DAYS` | `3, 1` | За сколько суток до конца подписки напоминать. Список через запятую |
| `UNPAID_INVOICE_AFTER_MINUTES` | `30` | Через сколько минут напомнить о неоплаченном счёте. Допустимо от 5 до 1440 |
| `BROADCAST_RATE_PER_SECOND` | `25` | Темп рассылки. Выше 30 нельзя — это предел Telegram, и запас нужен сервисным уведомлениям |
| `WINBACK_STEPS_DAYS` | `1, 3, 14, 30` | На какие сутки после истечения уходят ступени лесенки возврата |
| `WINBACK_PROMO_PERCENT` | `30` | Размер личной скидки второй ступени |
| `WINBACK_PROMO_TTL_HOURS` | `72` | Сколько живёт личный промокод второй ступени |
| `WINBACK_FREE_DAYS` | `3` | Сколько дней доступа дарит третья ступень |
| `WINBACK_COOLDOWN_DAYS` | `180` | Не чаще одной лесенки в этот срок |

Пороги `EXPIRY_REMINDER_DAYS` не произвольны: каждое значение превращается в
вид уведомления `expiring_<дни>`, а у вида должны быть тексты на всех языках.
Сейчас тексты есть для `3` и `1`; добавляя новый порог, добавьте и их, иначе
уведомление упадёт при отправке живому человеку.

`WINBACK_COOLDOWN_DAYS` меньше срока подписки ставить не стоит: без него
истечение превращается в способ заработка — дал подписке кончиться, забрал
бесплатные дни, повторил.

### Фоновые задачи

Расписание задаётся в коде и выполняется сервисами `scheduler` (ставит) и
`worker` (выполняет). Работать должны оба.

| Задача | Расписание | Что делает |
|---|---|---|
| `process_outbox` | каждую минуту | Разбирает очередь: уведомления, выдача доступа в панели, темы поддержки |
| `run_broadcast` | каждую минуту | Отправляет очередную пачку идущей кампании, выдерживая темп |
| `reconcile_pending_payments` | каждые 5 минут | Добирает оплаты, подтверждённые провайдером, если вебхук потерялся |
| `attempt_auto_renewals` | каждые 10 минут | Отрабатывает подошедшие циклы автопродления |
| `expire_subscriptions` | в начале часа | Переводит просроченные подписки в `expired` и снимает доступ |
| `notify_subscription_events` | каждый час на 7-й минуте | Ставит напоминания об окончании подписки и о неоплаченном счёте |
| `reconcile_panel` | раз в `RECONCILE_INTERVAL_HOURS` | Сверяет наше состояние с панелью и записывает расхождения |
| `run_winback` | ежедневно в 9:23 UTC | Ставит очередную ступень лесенки возврата |

Смещения от круглых значений намеренные. Напоминания идут на седьмой минуте,
потому что в ноль работает истечение подписок: запуск встык дал бы напоминание
про состояние, которое меняется прямо сейчас. Лесенка уходит днём, а не ночью:
письмо про возвращение, пришедшее в три часа ночи, к утру уже погребено под
остальной почтой.

## 11. Обновление

```bash
git pull
docker compose build
docker compose up -d
```

Миграции применяет сервис `migrate` до старта остальных — вручную ничего запускать
не нужно.

MiniApp обновляется у пользователей сам: nginx отдаёт `/app/` с `Cache-Control:
no-cache`, поэтому клиент каждый раз спрашивает, не изменилась ли точка входа, а
файлы сборки с хешем в имени хранит вечно. Если приложение всё же осталось на
старой сборке, значит копия попала в кэш клиента ещё до появления этих
заголовков — очистите кэш Telegram (Настройки → Данные и память → Использование
памяти → Очистить кэш) или откройте MiniApp по адресу с новым параметром,
например `https://ваш-домен/app/?v=2`.

## Диагностика

| Симптом | Причина |
|---|---|
| `migrate` завершается с ошибкой | Недоступен Postgres или неверный `DATABASE_URL` |
| `/health` отдаёт `database: false` | Контейнер базы не поднялся, смотрите `docker compose logs postgres` |
| Бот не отвечает | Проверьте `BOT_WEBHOOK_BASE_URL`, TLS и `docker compose logs bot` |
| Бот пишет `Unauthorized: invalid token specified` | Неверный `BOT_TOKEN`, возьмите его заново у @BotFather |
| Задачи не выполняются | Работать должны оба сервиса: `worker` и `scheduler` |
| Уведомления приходят с задержкой | Очередь не успевает разбираться: `docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select count(*) from outbox where processed_at is null"'`. Если число растёт от прогона к прогону, поднимите `OUTBOX_BATCH_SIZE` |
| Обращения не появляются в супергруппе | `docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select topic, last_error from outbox where processed_at is null order by id limit 20"'`. Застрявшие строки с темой `support.outbound` и отказом `createForumTopic` в `last_error` означают, что у бота нет права управления темами |
| Кнопки «Написать в поддержку» нет | Пуст `SUPPORT_CHAT_ID` — поддержка выключена целиком |
| Рассылка стоит на месте | Идёт другая кампания: их отправляют строго по одной. Статус видно в `/admin/broadcasts`, счётчики обновляются на ходу |
| Панель не отвечает | Проверьте `REMNAWAVE_TOKEN` и сетевую доступность из контейнера `api` |
| Вход через Telegram возвращает на `/login?error=token_invalid` | Redirect URI в BotFather не совпадает с `https://ваш-домен/api/auth/telegram/callback` либо прокси режет cookie `repibot_oidc` |
| Кнопки «Войти через Telegram» нет | Пуст `TELEGRAM_OIDC_CLIENT_ID` |
| Ключи доступа перестали пускать | Сменился домен: RP ID выводится из `PUBLIC_WEB_URL`, ключи нужно завести заново |
| MiniApp ведёт себя как до обновления, а сайт обновился | В кэше клиента старая точка входа: очистите кэш Telegram или откройте `/app/?v=<число>` |
